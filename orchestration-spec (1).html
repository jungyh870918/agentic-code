§ 00 — Overview

개요와 범위

무엇을 만들고, 무엇을 의도적으로 만들지 않는지를 먼저 정한다.

00.1프로젝트 목표

이 프로젝트의 산출물은 앱이 아니라 오케스트레이션 시스템과 그 능력의 증명이다. 그래서 만드는 서비스는 화려할 필요가 없고, 오케스트레이션이 잘 돌아간다는 걸 보여주기 좋으면 된다. 증명의 핵심은 코드 품질이 아니라 프로세스 추적 가능성 — "이 결과물은 누가, 어떤 판단으로, 왜 만들었는가"가 GitHub 안에 기록으로 남아야 한다.

00.2역할 분포

사람과 에이전트가 책임을 어떻게 나누는지의 최상위 그림이다.

00.3의도적으로 제외한 것

블로그·외부 일지 작성은 이 시스템의 흐름에 포함하지 않는다. 사람이 읽는 기록은 오직 타 팀 교류용 이력의 목적으로만 남기며, 그 기록은 GitHub 안의 PR 설명·이슈 코멘트·CHANGELOG·ADR로 인라인화한다. 별도 사이트나 외부 채널은 컨텍스트에 포함하지 않는다 — 곁다리가 본류를 막을 위험을 차단한다.

Principle

"이 PR은 사람이 한 줄도 안 썼습니다"를 증명 가능한 주장으로 만든다.
기록이 없으면 마법상자고, 회사는 마법상자를 도입하지 않는다.

§ 01 — Governance

자동화의 경계를 긋다

코드보다 경계가 먼저다. 기술적으로 가능한 것과 거버넌스적으로 해도 되는 것은 다르다.

01.1여섯 개의 설계 축

오케스트레이션을 한 방향에서만 보면 놓치는 게 많아 여섯 각도로 쪼갠다. 앞 셋은 구조축, 뒤 셋은 횡단 원칙이다.

축질문역할
권한누가 결정하는가레이어를 4단으로 분리
신뢰 경계어디까지 내 영역인가같은 작업도 위치로 허용 수준이 다름
가역성되돌릴 수 있는가실무 라우팅의 실제 알고리즘
관찰 가능성전부 기록했는가증명의 원천 · 게이트를 1초로 압축
에스컬레이션막혔을 때 어디로윗 레이어로 — 멋대로 진행 금지
상태·행동 분리진실은 어디 있는가외부(GitHub) · 메모리 의존 금지

01.2권한 레이어 — 누가 결정하는가

결정권의 소재로 시스템을 네 층으로 가른다. 위로 갈수록 자동화는 가능해도 해서는 안 되는 영역, 아래로 갈수록 사람의 손이 떠난다.

01.3신뢰 경계 — 어디까지가 내 영역인가

권한 축이 수직이라면 신뢰 경계는 수평이다. 같은 작업이라도 어디서 일어나느냐에 따라 자동화 허용 수준이 달라진다.

  • 내부 구역 — 내가 오너인 코드. 실행 레이어를 마음껏 자동화하는 운동장.
  • 경계 구역 — 공유 라이브러리·API 계약. 출력이 경계를 넘기 전 사람 게이트가 한 번 들어간다.
  • 외부 구역 — 타 팀·프로덕션. 에이전트는 읽기만, 쓰기와 소통은 사람을 통해서만.

이 분할이 회사 도입 가능성을 결정짓는다. 타 팀이 봤을 때 "사람을 대체하는 위험한 자동화"가 아니라 "팀 생산성을 N배 올리는 도구"로 포지셔닝되기 때문이다.

01.4가역성 — 게이트를 정하는 실제 기준

새 작업이 들어오면 단 하나만 묻는다 — "이게 잘못되면 되돌리는 데 얼마 드는가?" 이 질문 하나로 어느 게이트로 보낼지 즉시 결정된다.

등급예시되돌림 비용처리
자유 가역코드 변경, 문서, 브랜치git revert · 1분완전 자동
비용 있는 가역스테이징 배포, 테스트 데이터흔적·시간 소요자동 + 로그
준 비가역프로덕션 배포, 운영 DB매우 어려움사람 게이트
비가역데이터 삭제, 시크릿, 결제불가게이트 + 확인

01.5횡단 원칙 셋

  • 관찰 가능성 — 모든 에이전트 행동은 누가·무엇을·왜를 GitHub에 남긴다. 이 기록이 있어야 게이트가 1초가 된다.
  • 에스컬레이션 — 막히면 멈추고 윗 레이어로 올린다. "어떻게든 통과시키려" 테스트를 약화시키지 않는다.
  • 상태·행동 분리 — 진실의 원천은 외부(GitHub)에 둔다. 한 에이전트가 죽어도 다른 에이전트가 상태만 보고 이어받는다.
§ 02 — Architecture

오케스트레이션 아키텍처

사람-헤더-전문 에이전트-자동화의 네 계층과, 각각의 책임 경계.

02.1헤더의 네 가지 역할

메인 오케스트레이터(Claude)는 직접 코드를 많이 짜는 주체가 아니라 지휘자다. 역할은 명확히 네 가지로 한정한다.

  • 작업 분해 — GitHub 상태(이슈·라벨)를 읽고 큰 요청을 실행 단위로 나눈다.
  • 라우팅 — 각 단위를 가역성과 성격에 따라 적절한 전문 에이전트(또는 사람)에게 보낸다.
  • 검증 — 돌아온 결과물이 행동 규약과 스펙에 부합하는지 확인한다.
  • 트리거 — 다음 단계를 GitHub 상태에 기록해 자동 발화시킨다.

02.2채팅방은 실행 무대가 아니다

채팅방은 휘발성 컨텍스트라 진실의 원천이 될 수 없다. 길어지면 잘리고, 닫히면 사라지고, 두 방이 서로를 못 본다. 그래서 에이전트의 실행 무대는 채팅이 아니라 GitHub Actions 안에서 호출되는 무상태 Claude API다. 맥락은 매번 GitHub에서 읽어 프롬프트에 주입한다.

Decision

채팅방은 사람 쪽 도구일 뿐이다. 실행 단위로 늘리지 않는다. 권장 구성: 설계·상의 방 1개 + 작업 지시 방 1개. 다리는 채팅 기억이 아니라 GitHub.

§ 03 — Coordination

조율 모델

에이전트는 서로 대화하지 않는다. 상태를 통해 간접적으로 조율된다.

03.1상태 기반 간접 통신

여러 에이전트가 직접 메시지를 주고받으면 동기화 지옥에 빠진다. 그래서 통신을 상태(GitHub 이슈 라벨·PR 체크·코멘트)를 매개로 한 간접 통신으로 단순화한다. 각 에이전트는 상태를 읽어 자기 차례인지 판단하고, 일을 마치면 상태를 갱신한다.

§ 04 — Tool Stack

도구 스택과 각 도구의 책임

Git · GitHub Actions · Terraform · Claude API · MCP — 다섯 도구가 어떻게 맞물리는가.

도구레이어책임
Git 버전 · 협업 모든 변경의 1차 진실. 브랜치·커밋·이력이 곧 시스템의 기억.
GitHub Actions 트리거 · 자동화 PR·이슈·테스트 이벤트를 받아 파이프라인을 발화. 에이전트 실행 무대 호스트.
Terraform 인프라 코드화 (Phase 3) AWS 리소스를 코드로 선언·관리. 에이전트가 인프라까지 다루게 하는 핵심.
Claude API 판단 · 생성 헤더와 전문 에이전트의 두뇌. 무상태 호출, 맥락은 매번 주입.
MCP 상태 접근 에이전트가 GitHub 상태를 직접 읽고 쓰는 표준 통로. 상태 기반 조율의 실제 구현.

04.1Terraform이 들어가는 자리

Phase 1·2에서는 Terraform이 필요 없다. AWS도 마찬가지다. 인프라가 들어오는 시점은 Phase 3 — 그때 VPC·EKS·ECR·IAM·ALB·RDS·Secrets Manager·모니터링 스택을 모두 코드로 선언한다. 사전 학습은 이미 다음 수준까지 정리되어 있다.

  • 개념 — provider, resource, module, backend(S3), variables, outputs, 의존관계.
  • 리소스 — VPC, EKS(IRSA), ECR(lifecycle), IAM, ALB(Ingress Controller).
  • 연동 — Terraform output → GitHub Actions Secrets, ECR login → kubectl set image.
  • 미학습 — workspace, data source, RDS, ECS, Secrets Manager 연동, Prometheus + Grafana.

미학습 영역은 Phase 3에서 에이전트가 작성한 코드 → 사람이 검토 → 학습이 동시에 일어나는 구조로 채운다. 이 자체가 또 하나의 증명 포인트다.

§ 06 — Phase 1 Implementation

Phase 1 구현 — PR 자동 리뷰

첫 자동화는 가역성이 가장 높고 가치가 즉시 보이는 PR 자동 리뷰부터.

06.1사전 준비물

  • GitHub 계정과 프라이빗 샌드박스 레포 한 개.
  • Anthropic API 키 — console.anthropic.com에서 발급.
  • Node.js 환경 (맥미니 또는 로컬).

AWS는 이 단계에서 필요 없다. 인프라는 Phase 3까지 미룬다.

06.2레포 구조 (최소)

// 모노레포 — Phase 1 시점의 최소 골격
repo-root/
├─ .github/workflows/pr-review.yml    // PR 트리거되는 단 하나의 워크플로
├─ orchestrator/
│   ├─ review.mjs                     // diff 읽고 Claude 호출, 코멘트 게시
│   └─ package.json                   // @anthropic-ai/sdk 의존성
├─ CLAUDE.md                          // 에이전트 행동 규약
└─ src/                               // 리뷰 대상이 될 데모 앱 코드

apps/ packages/ 등은 Phase 2에서 추가한다.

06.3세팅 순서

  1. 레포 생성 — 위 골격을 빈 채로 올린다.
  2. Secret 등록 — Settings → Secrets and variables → Actions에 ANTHROPIC_API_KEY로 등록. 코드에 절대 적지 않는다.
  3. 워크플로 활성화 — pr-review.yml이 pull_request 이벤트에 반응하도록 설정.
  4. 스크립트 동작 — PR diff를 GitHub API로 가져와 CLAUDE.md와 함께 Claude에 보내고, 응답을 PR 코멘트로 게시.
06.4 .github/workflows/pr-review.yml
name: PR Auto Review
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  pull-requests: write   # 코멘트 게시에 필요

jobs:
  review:
    runs-on: ubuntu-latest   # 나중에 self-hosted(맥미니)로 교체 가능
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0      # diff 비교 위해 전체 히스토리

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install deps
        working-directory: orchestrator
        run: npm install

      - name: Run review
        working-directory: orchestrator
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          PR_NUMBER: ${{ github.event.pull_request.number }}
          REPO: ${{ github.repository }}
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
        run: node review.mjs
06.5 orchestrator/review.mjs
import Anthropic from "@anthropic-ai/sdk";
import { execSync } from "node:child_process";
import { readFileSync } from "node:fs";

const { ANTHROPIC_API_KEY, GITHUB_TOKEN, PR_NUMBER,
        REPO, BASE_SHA, HEAD_SHA } = process.env;

// 1) diff 추출 — 자유 가역(읽기)
const diff = execSync(`git diff ${BASE_SHA} ${HEAD_SHA}`,
  { maxBuffer: 10 * 1024 * 1024 }).toString();

// 2) 행동 규약 로드
let rules = "";
try { rules = readFileSync("../CLAUDE.md", "utf8"); }
catch { rules = "(규약 파일 없음)"; }

// 3) Claude 호출 — 헤더의 판단
const client = new Anthropic({ apiKey: ANTHROPIC_API_KEY });
const msg = await client.messages.create({
  model: "claude-opus-4-7",   // 작업 시점 최신으로 갱신
  max_tokens: 2000,
  system: `너는 코드 리뷰 에이전트다. 행동 규약을 따른다.\n\n${rules}\n\n` +
          `리뷰는 한국어로, (1) 변경 요약 (2) 발견 문제와 근거 ` +
          `(3) 리스크 평가 (4) 머지 가능 여부. 추측 금지, 근거만.`,
  messages: [{ role: "user",
               content: `다음 PR diff를 리뷰하라:\n\n\`\`\`diff\n${diff}\n\`\`\`` }],
});
const review = msg.content.filter(b => b.type === "text")
                          .map(b => b.text).join("\n");

// 4) PR 코멘트 게시 — 관찰 가능성(누가·무엇을·왜)
const body = `## 자동 코드 리뷰 (Claude)\n\n${review}\n\n` +
             `---\n_모델: claude-opus-4-7 · 트리거: pull_request · ` +
             `이 리뷰는 에이전트가 생성했습니다._`;

const res = await fetch(
  `https://api.github.com/repos/${REPO}/issues/${PR_NUMBER}/comments`,
  {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${GITHUB_TOKEN}`,
      "Accept": "application/vnd.github+json",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ body }),
  }
);

if (!res.ok) {
  console.error("코멘트 게시 실패:", res.status, await res.text());
  process.exit(1);
}
console.log("리뷰 코멘트 게시 완료.");
06.6 CLAUDE.md — 행동 규약
# 에이전트 행동 규약

## 권한 레이어
- 의도: 사람 전용 (에이전트 입력 불가)
- 판단: 에이전트는 근거 제출까지, 결정은 사람
- 실행: 에이전트 자율
- 기계: 완전 자동

## 신뢰 경계
- 내부 구역: 실행 자동 자유
- 경계 구역: 출력 전 사람 게이트
- 외부 구역: 읽기만, 쓰기·소통은 사람

## 가역성 라우팅
- 자유 가역: 완전 자동
- 비용 있는 가역: 자동 + 로그
- 준 비가역: 사람 게이트
- 비가역: 게이트 + 추가 확인

## 횡단 원칙
- 관찰 가능성: 누가·무엇을·왜를 GitHub에 남긴다
- 에스컬레이션: 막히면 멋대로 진행 말고 윗 레이어로
- 상태/행동 분리: 진실의 원천은 GitHub 상태

## 타 팀 교류 이력
- PR 설명에 변경 목적·영향 범위·근거를 사람이 읽도록 작성
- 경계/외부 구역 변경은 사람이 소통, 에이전트는 초안만

06.7검증 기준 — Phase 1 완료 조건

  • PR을 열면 1~2분 내 자동 리뷰 코멘트가 달린다.
  • 코멘트에 모델·트리거·"에이전트 생성" 표기가 남는다 (관찰 가능성).
  • API 키가 코드 어디에도 없고 Secret으로만 주입된다.
  • 데모로 "이 리뷰는 사람이 쓰지 않았다"를 보여줄 수 있다.

이게 통과되면 같은 패턴으로 이슈→스펙 초안, 테스트 실패 분석, Swagger 자동 생성을 차례로 붙인다.

§ 07 — Roadmap

로드맵 — 능력을 단계적으로 쌓는다

각 단계는 앞 단계의 신뢰 위에 쌓인다. 자동화 범위가 넓어질수록 사람 게이트의 위치도 정교해진다.

PHASE 01 파이프라인 증명 2~3주 · 진행

"에이전트가 개발 프로세스에 참여한다"의 최소 증명. GitHub Actions + Claude API 조합만 사용.

  • PR 자동 리뷰 (가장 먼저 — 가역성 최고)
  • 이슈 → 스펙 문서 초안 자동 생성
  • 테스트 실패 → 원인 분석 + 수정 제안
  • 새 API 엔드포인트 → Swagger 문서 갱신
PHASE 02 멀티 에이전트 파이프라인 3~4주 · 예정

한 기능이 사람 터치 최소화로 흐르는 파이프라인. 멀티 모델 라우팅 도입.

  • 이슈 등록 → Claude가 스펙 분해 → 서브태스크 생성
  • Cursor/v0가 코드 작성 → Claude 리뷰 + 테스트 생성
  • GitHub Actions 자동 테스트 → 머지 가능 상태까지
  • 사람은 마지막 승인 버튼만 누른다 (1초 게이트)
PHASE 03 엔터프라이즈 스택 완성 4~6주 · 예정

인프라까지 에이전트가 관리하는 완전한 구조. Terraform이 이 단계에서 본격 등장.

  • Terraform IaC로 AWS 인프라 코드화 (VPC·EKS·RDS·ECR)
  • Secrets Manager 연동 · IAM·IRSA 자동 바인딩
  • Prometheus + Grafana 모니터링 스택
  • ECR 이미지 취약점 스캔 + SAST 보안 자동화
  • 로드 테스트 자동화 · 필요 시 LangGraph 검토
§ 08 — Standards Alignment

업계 표준 대비 판단

이 명세의 제약과 선택이 업계 관행과 어떻게 맞물리는지 정직하게 점검한다.

부합

최종 승인은 사람

오히려 이걸 안 지키면 비표준이다. GitHub의 브랜치 보호 규칙, 필수 리뷰어, 자가승인 금지는 거의 모든 기업의 기본 거버넌스. "AI가 코드를 짜는 시대에도 머지 승인은 사람" — 이 라인은 흔들리지 않는다.

모범

사람이 읽는 기록을 PR·이슈·ADR로 한정

외부 블로그를 흐름에서 빼고 GitHub 안의 표준 산출물(PR 설명·코멘트·CHANGELOG·ADR)로 좁힌 결정은 성숙한 팀일수록 챙기는 관행이다. 복잡도를 줄이면서 표준에 더 가까워졌다.

합의선

코드·리뷰·테스트는 자동, 머지·배포·타팀 소통은 사람

GitHub Copilot 류 AI 코드 리뷰 도구들이 정확히 이 선에서 작동한다. 시장의 검증된 합의선과 일치한다.

보수적

멀티 모델 라우팅을 Phase 2로 미룸 — 전략적 보강 필요

능력 증명이 목표인 만큼 "멀티 모델 오케스트레이션"은 강력한 차별점이다. Phase 1이 너무 길어지면 증명이 밋밋해진다. 절충안 — Phase 1 끝에 값싼 보조 작업(커밋 요약) 하나만 로컬 LLM으로 붙여 "라우팅이 존재함"의 최소 증명을 보여준다. 전체 멀티 모델은 Phase 2.

보강

관찰 가능성의 깊이

지금은 "코멘트에 모델·트리거 표기"까지다. 성숙한 시스템은 구조화된 메타데이터(프롬프트 버전·토큰 사용량·비용·소요 시간)를 함께 남긴다. Phase 1에선 지금 수준으로 충분하지만, "추적 가능성이 증명 포인트"라면 Phase 2에서 JSON으로 PR에 첨부하거나 별도 로그로 남기는 보강을 권한다.

Verdict

이 설계는 "데모로 멋진" 쪽보다 "회사에 도입되는" 쪽으로 잘 기울어 있다. 그게 맞는 방향이다.
