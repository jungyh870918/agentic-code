§ 01 — Plan B

B 플랜의 실체

우리 명세서(R2)와 저쪽 튜터 답변에서 채택한 네 가지 흡수 지점, 그리고 그것이 파일과 시나리오로 어떻게 실체화되는지.

B 플랜의 목표는 하나다. 우리 명세서 R2의 야심(재귀 자기 검증, Phase 로드맵, 신뢰 축적 이론)을 유지하되, 저쪽 튜터가 제시한 실무 강도(권한 강제, 위험 등급 정량화, 정량적 중단 조건, PR 템플릿)를 흡수해 실행 가능한 청사진으로 완성한다.

1.1흡수한 네 지점

  • 권한 강제의 이중 구조 — CLAUDE.md는 지침, .claude/settings.json과 hooks가 실제 강제. 명세서에 원칙만 있고 강제 층이 없으면 실효성이 없다.
  • 위험 등급 R0~R3 — 우리 가역성 4단(자유/비용/준비/비가역)을 R0~R3로 이름 붙여 실무 언어와 정합. PR 템플릿·라벨·자동 리뷰에 이 등급이 표면화된다.
  • 정량적 중단 조건 — "막히면 올려보낸다" 원칙에 임계치를 부여. 테스트 2회 실패, 수정 루프 2회 초과, 변경 파일 15개 이상 등. 이 수치가 있어야 원칙이 실행 가능해진다.
  • PR 템플릿의 강제 필드 — "변경하지 않은 범위", "미검증 사항", "롤백 방법", "위험 등급"이 모든 PR의 필수 필드. 관찰 가능성의 실체화.

1.2유지한 우리 관점

  • 증명 프로젝트의 정체성 — Phase 3까지 가는 여정 자체가 산출물이다. 저쪽은 회사 도입 청사진이지만 우리는 능력 증명이라는 야심을 유지.
  • 재귀 자기 검증 — 저쪽에는 없는 개념. 시스템이 자기 자신의 다음 버전을 자기 원칙으로 검증한다는 특성을 살린다.
  • 신뢰 축적 이론 — Phase 이동의 시점을 "관찰된 PR 수"로만 정하지 않고 신뢰 축적이라는 개념적 근거로 뒷받침.
Plan B — 요약

명세서 R2 → R2.5로 개정하고, kit에 4개 파일을 즉시 추가한다. Phase 1은 얇게 시작하되 강제 층은 확보한 상태. 나머지 파일들은 신뢰 축적에 따라 Phase 2·3에서 점진 추가.

§ 03 — Guidance Layer

파일별 명세 · 지침 층

에이전트가 읽어서 행동을 유도받는 문서들. Claude가 매 세션에서 참조하는 자리.

CLAUDE.md Baseline · Refined P1
목적
에이전트의 매 API 호출에서 시스템 프롬프트로 주입되는 행동 규약의 실행용 압축본. 명세서의 원칙을 Claude가 흡수 가능한 형태로 정리한 것.
크기
150~300줄 이하. 백과사전이 아니라 라우팅 규칙. 각 도메인 상세는 하위 문서로 링크.
담을 것
프로젝트 목적 · 저장소 구조 · 기본 개발 명령 · 변경 절차 · 권한·가역성 원칙 · 테스트 기준 · 금지 행동 · PR 완료 조건 · 하위 문서 위치 · 중단 조건 참조
담지 말 것
모든 서비스 상세 설명 · API 명세 전체 · 과거 의사결정 대화 · 긴 코딩 스타일 · 수십 개의 예외 규칙
중요 참조
이 문서는 지침 층이며 실제 권한 강제는 .claude/settings.json과 hooks가 담당한다. "말로 하지 말라"와 "실제로 못 하게 한다"를 구분한다.

§ 04 — Enforcement Layer

파일별 명세 · 강제 층

지침이 무시되거나 잘못 해석돼도 실행 자체를 차단하는 층. CLAUDE.md의 원칙이 실효성을 갖게 되는 자리.

.claude/settings.json Phase 1 · 즉시 추가
목적
Claude Code의 실행 계층에서 강제되는 권한 규칙. defaultMode + allow/ask/deny 배열로 구성.
평가 순서
deny → ask → allow. deny가 최우선.
버전
팀 공용은 .claude/settings.json, 개인 기계별은 .claude/settings.local.json, 개인 전역은 ~/.claude/settings.json.
실효성
모델의 지시가 아니라 Claude Code 실행 계층에서 강제된다. 모델이 어떻게 해석하든 여기서 걸리면 실행이 차단된다.
SPEC 04.1 settings.json 방향 예시
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git log *)",
      "Bash(npm test *)",
      "Bash(npm run lint *)",
      "Bash(npm run typecheck *)"
    ],
    "ask": [
      "Bash(git commit *)",
      "Bash(git push *)",
      "Bash(npm install *)",
      "Bash(npm add *)",
      "Bash(kubectl *)",
      "Bash(helm *)",
      "Bash(terraform apply *)"
    ],
    "deny": [
      "Bash(git push --force *)",
      "Bash(git reset --hard *)",
      "Bash(git clean -fd *)",
      "Bash(rm -rf /*)",
      "Bash(kubectl delete *)",
      "Bash(terraform destroy *)"
    ]
  }
}
권한 강제의 원칙

규약을 만들 때 스스로에게 묻는다 — "이 원칙이 지켜지지 않아도 아무 일이 일어나지 않는가?" 답이 그렇다면 그 원칙은 지침 층에만 있는 상태. 반드시 강제 층에 대응하는 규칙을 추가해야 한다.

.claude/hooks/guard-command.sh Phase 1 · 즉시 추가
목적
PreToolUse 훅. 명령이 실행되기 전 shell 스크립트가 검사. force push, hard reset, 광범위 삭제, 운영 namespace, 운영 DB URL, .github/workflows/ 수정, secrets 접근 등을 판정.
결과
allow / ask / deny 중 하나를 반환.
구현
LLM 훅이 아니라 결정적 shell/TypeScript 규칙. 판정에 언어 모델을 개입시키지 않는다.
.claude/hooks/validate-write-scope.sh Phase 1 · 즉시 추가
목적
파일 편집 전 편집 범위 검사. 현재 task에 허용된 디렉토리인지, 생성 파일인지, protected file인지, 변경 파일 상한(15개)을 넘었는지 검사.
보호 대상
.github/workflows/** · CODEOWNERS · .claude/settings.json · infra/** · migrations/** · 비즈니스 로직 도메인 폴더
기본 편집 영역
대상 서비스 디렉토리 + common/ (경계 구역은 사람 승인 필요)
.claude/hooks/format-changed-file.sh Phase 2
목적
PostToolUse 훅. 변경된 파일 하나에만 포맷 적용. 저장소 전체 포맷은 diff를 부풀리므로 절대 금지.
예시
잘못된 형태: npm run prettier -- --write . / 올바른 형태: prettier --write <changed-file>
.claude/hooks/record-run-event.sh Phase 2
목적
구조화된 실행 이벤트 로그. 관찰 가능성의 실체.
기록 이벤트
session_started · plan_approved · file_modified · verification_started · verification_completed · permission_denied · task_completed · task_failed
저장 위치
로컬은 .agent-runs/(gitignore). CI에서는 GitHub Actions artifact.
스키마
runId, taskId, event, baseSha, headSha, command, result, durationMs, timestamp
.github/CODEOWNERS Phase 1 · 즉시 추가
목적
민감 파일 변경 시 자동 리뷰어 지정. GitHub이 강제한다.
소유자
개인 프로젝트라도 본인 계정으로 지정. 목적은 사람 수가 아니라 민감 파일을 일반 변경과 구분하는 것.

7.4MCP 도입 순서

MCP 원칙

초기 MCP는 하나 이하. 로컬에서 이미 사용 가능한 것(git, gh CLI, GitHub Actions)이 있으면 MCP 안 붙인다. 복사·붙여넣기가 반복되기 시작하면 그때 GitHub read-only MCP부터.

MCP도입 시점범위
GitHubPhase 2 초반read 중심 (issue/PR/review 조회). write는 매번 승인.
SentryPhase 3read-only. 관련 오류 조회, 배포 후 회귀 확인. write 권한 절대 금지.
PlaywrightPhase 3Playwright 테스트 스위트가 먼저 있어야. 실패 화면 탐색, 재현 보조.
KubernetesPhase 3 후반 (조건부)local kind/minikube read → staging read → staging 제한 write → production read. Production write는 원칙적으로 사람 전용.
Database제한적로컬 DB · fixture DB · read replica · schema metadata · 익명화 샘플까지만. 운영 write는 절대 금지.

9.1진입 조건

Phase 2로 넘어가는 것은 시점(Phase 1이 끝났나)이 아니라 신뢰(관찰된 게 충분한가)가 결정한다. 최소 기준:

  • 10~20개 PR 처리 완료 — 자동 리뷰의 실제 품질을 판단할 수 있는 표본 확보
  • AI finding 채택률 40% 이상 — 자동 리뷰가 노이즈 이상의 가치를 제공
  • revert 비율 5% 이하 — 머지 판단이 정확
  • 중단 조건 트리거 이력 — 최소 1~2회 자동 중단이 실제로 작동한 사례
  • docs/agentic-development/ 5개 문서 존재 — Phase 2 자동화가 참조할 근거 완비

9.3바뀌는 사이클 · 라벨로 시작하는 흐름

9.4실제 변환 작업

  • client JavaScript → TypeScript 마이그레이션 — 7~10개 서브 PR
  • 공통 미들웨어 추출 — 서비스별 흩어진 미들웨어를 common/으로. 경계 구역 변경이라 사람 게이트 강화
  • 결제 흐름 멱등성 강화 — Stripe 처리에 중복 방지 로직. 비즈니스 로직 근처를 만지는 미묘한 작업
  • NATS Streaming → Kafka 이관 — Phase 2의 최대 변환. 5~7개 서브 PR로 분할 (서비스별 이관)

Phase 3 진입과 완결

인프라 자동화. 넓어지면서 조여지는 시기.

Phase 03 인프라 자동화 — IaC와 사람 게이트 재배치 Week 8~13 (4~6주)

목표: 17개 매뉴얼 k8s YAML을 에이전트가 Terraform 모듈로 변환. DigitalOcean → AWS EKS 이전. 자동화가 넓어지면서 사람 게이트는 새로 강화.

완료 조건: 인프라 변경이 .tf PR로 흐름, Plan 자동 리뷰, Apply 사람 명시 실행, AWS EKS 안정 운영, 사람이 kubectl을 매뉴얼로 치지 않는 상태 4주 이상.

10.1진입 조건

  • Phase 2의 코드 변환이 최소 2회 성공적으로 완결 (예: JS→TS 마이그레이션, Kafka 이관)
  • 자동 코드 생성의 revert 비율 5% 이하 유지
  • 보안 스캔 통합이 안정적으로 작동
  • ADR 최소 3개 (Kafka, TS 마이그레이션, Terraform 채택)

10.3인프라 사이클 · Merge와 Apply의 분리

Phase 3의 결정적 차이. Merge = plan 승인, Apply = 실제 인프라 변경. 두 개의 사람 게이트.

  1. 이슈 — gh issue create --label "phase-3,infra,ready-for-draft"
  2. 자동 코드 생성 — code-draft.yml이 Terraform 모듈 초안 작성, PR 오픈
  3. 병렬 리뷰 — pr-review.yml (코드 관점) + terraform-plan.yml (인프라 관점). 각각 별도 코멘트로 게시
  4. Plan 결과 검토 — 추가 리소스 · 변경 · 삭제 목록, 월 예상 비용, 리스크 평가 확인
  5. Merge (게이트 1) — 코드가 옳다는 승인. 하지만 실제 인프라는 아직 변경 안 됨
  6. Apply 트리거 (게이트 2) — gh workflow run terraform-apply.yml --field environment=dev. 사람이 명시적으로 실행
  7. Apply 실행 관찰 — 러너가 apply 실행. 5~30분 소요. 실시간 로그.
  8. Dev 검증 — Grafana 대시보드 · 통합 테스트. 문제 없으면 staging 반복
  9. Staging apply — 24시간 관측 창 후 prod로
  10. Prod apply — 배포 창 조율, 트래픽 낮은 시간. 실시간 관측 강화. 문제 감지 시 즉시 롤백 판단
Apply 게이트의 원칙

Apply는 어떤 상황에서도 자동 트리거 금지. 이유는 명세서 § 01.4 가역성 원칙 — 인프라 변경은 준 비가역이며, 프로덕션은 사용자 영향이 즉시 발생. Claude가 plan을 해석해서 리스크 요약을 미리 제공하지만, apply 결정은 조직 맥락(배포 창 · 트래픽 · 다른 진행 작업)을 아는 사람만 할 수 있음.

10.4Phase 3의 최대 변환들

  • k8s YAML 17개 → Terraform 모듈 — 서비스별 · DB · Ingress · NATS·Kafka. 각 모듈이 별도 PR로.
  • DigitalOcean → AWS EKS 이전 — Phase 3의 정수. Stage 1~7로 분할된 마이그레이션 계획서. Blue-Green 방식.
  • Prometheus + Grafana 자동 셋업 — Helm 차트를 Terraform 모듈로 감싸서 원클릭 설치
  • ECR 취약점 스캔 + SAST 통합 — 이미지 푸시 시 자동 스캔, 심각도 High 이상이면 배포 자동 실패
  • Secrets Manager 연동 · IAM/IRSA 자동 바인딩 — 파드별 세밀 권한
  • Blue-Green cutover 절차 — DNS 스위치 순간이 결정적
  • Drift Detection 워크플로 — IaC와 실제 상태 정기 대조

10.5완결 시점의 상태

Phase 3이 완결되면 시스템이 다음 상태에 도달한다.

  • 코드 작성부터 프로덕션 배포까지 전 과정이 관찰 가능하고 추적 가능
  • 각 단계에서 어떤 모델이 어떤 근거로 어떤 판단을 했는지 GitHub 영구 기록
  • 사람 역할은 실행에서 판단으로 완전히 이동 — 그 판단마저 Claude가 근거 정리
  • 회사 관점에서 감사 가능성 · 개발 속도 · 인프라 안전성 동시 확보
  • 명세서 R5 개정 완료. 회고 섹션에 여정 정리. ADR 10개 이상 축적.

§ 12 — Failure Playbook

실패 플레이북

중단 조건에 도달했을 때, 자동화가 잘못 판단할 때, revert가 필요할 때의 대응 절차.

12.1중단 조건 발동 시

상황즉시 조치후속 조치
같은 테스트 2회 실패자동 재시도 중단. 러너 종료이슈에 실패 원인 후보·시도한 것·선택지 코멘트로 게시. 사람 판단 요청
수정 루프 2회 초과브랜치에 needs-human-review 라벨 부착사람이 로컬 Claude Code로 개입해 직접 편집
변경 파일 15개 초과PR 자동 생성 중단이슈를 서브 이슈들로 분할 요청. 각 서브 이슈 별도 라벨
테스트 삭제·약화 시도훅에서 즉시 차단사람 개입 필수. 왜 이 테스트가 문제인지 이슈로 등록
보안·권한 영역 진입settings.json이 명령 차단R3 등급 이슈로 별도 등록. Phase 3 사이클로 처리

12.2Revert 절차

  1. 즉시 revert — 문제 발견 시 git revert <merge-commit>. main에 revert 커밋 생성.
  2. revert PR — 자동 리뷰가 revert에도 붙는다. 규약을 따르는지 확인.
  3. 원인 분석 이슈 — 왜 이 변경이 문제였는지, 자동 리뷰가 왜 놓쳤는지 별도 이슈로 등록.
  4. 규약 개정 검토 — 같은 유형이 재발하지 않도록 CLAUDE.md 또는 settings.json에 규칙 추가.
  5. 지표 기록 — revert 비율에 반영. Phase 이동 판단에 사용.

12.3인프라 Apply 실패 시 (Phase 3)

  1. 자동 롤백 워크플로 트리거 — terraform-apply.yml 실패 감지 시 즉시 이전 상태로 되돌리는 로직 실행.
  2. 영향 범위 확인 — Grafana 대시보드로 서비스 상태 확인. 실 사용자 영향 여부 판단.
  3. 이슈 등록 — 실패 원인 · 시도한 것 · 관찰된 영향을 상세히 기록.
  4. Prod 재시도 판단 — 사람이 조직 맥락 고려해 다음 배포 창 결정.
플레이북의 원칙

실패는 시스템의 결함이 아니라 시스템이 자기 한계를 인식했다는 증거다. 중단 조건이 작동한다는 것은 자동화가 성숙했다는 뜻. 실패 없이 계속 진행되는 자동화가 오히려 위험 신호다.
