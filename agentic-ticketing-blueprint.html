B 플랜 재구성판

이 문서는 Concepts R2 · Spec R3과 정합하는 실행 청사진이다. 개념서가 왜인지, 명세서가 무엇인지 다뤘다면 이 청사진은 어떻게 · 언제 · 어디에 · 어떤 상태에서를 다룬다. R1과의 결정적 차이는 Phase 1의 급진적 축소와 모든 항목에 채택 상태 표시다. 관찰 후 자동화 원칙과 초기 설계량의 충돌이 해소된다.

R1 → R2 재구성

R1이 Phase 1에서 15개 이상의 파일·제도를 초기부터 도입하려 했다면, R2는 필수 5개만 도입하고 나머지는 관찰 후 채택 원칙에 따라 뒤로 미룬다.

각 항목에 채택 상태가 명시된다 — 필수 안전 · 가설적 자동화 · 관찰 후 채택 · 설계만. 이 표시로 지금 실행하는 것과 미래 설계가 문서 안에서 구분된다. 흐름에는 spec-ready 게이트가 추가되고, 위험 판정은 5축 병기 방식으로 변경된다.

§ 01 — Restructure Intent

R2 개정의 취지

R1에서 무엇이 바뀌었고 왜 바뀌었는가.

R1은 좋은 방향의 청사진이었지만 하나의 자기 모순을 안고 있었다. "관찰 후 자동화"를 원칙으로 삼으면서 정작 관찰이 시작되기 전에 상당한 파일 구조를 확정했다는 것. Phase 1이 이름과 달리 얇지 않았다.

R2는 이 모순을 두 가지 방법으로 해소한다.

  • Phase 1 축소. 초기 필수를 CLAUDE.md · settings.json · guard-command.sh · pull_request_template.md · 기존 CI 연결의 다섯 개로 줄인다. CODEOWNERS · 상세 docs · 진단 자동화 등은 실제 위험·반복 패턴이 관찰된 후 추가된다.
  • 채택 상태 명시. 각 파일·자동화에 필수 안전 · 가설적 자동화 · 관찰 후 채택 · 설계만 네 상태 중 하나가 부여된다. 지금 만드는 것과 나중 만들 것이 구분된다.

추가로 개념서 R2 · 명세서 R3의 새 개념들이 청사진에 실체화된다.

  • 위임 계약 실체화 지점 — 각 파일이 계약의 어느 성분을 담는지 표로 정리 (§ 04).
  • spec-ready 게이트 — 흐름에 삽입 (§ 09).
  • 5축 위험 판정 — 자동 등급 산출 (§ 09).
  • 원칙과 구현의 분리 — 각 자동화에 Policy · Implementation · Alternatives 3단 (§ 08).
  • 학습 회로 실행 시나리오 — 관찰이 규약 개정으로 이어지는 실제 흐름 (§ 13).
  • 지표를 위험 등급별로 세분화 — R0~R3 각각 다른 기대치 (§ 14).
이 문서의 두 개 갈래

이 청사진은 두 갈래로 읽힌다. 지금 실행하는 것은 § 05 (Phase 1 필수 5개), § 09 (게이트), § 10 (Phase 1 시나리오)에 있다. 미래 설계는 § 06, § 07, § 11, § 12에 있으며 채택 상태 뱃지로 구분된다.

§ 02 — Adoption States

채택 상태 4단

각 항목이 지금 어떤 상태에 있는지 표시하는 네 개의 라벨.

R2에서 도입되는 핵심 개념. 모든 파일·자동화·정책은 다음 네 상태 중 하나에 속한다. 이 상태가 명시되지 않으면 그 항목은 "미래 계획"과 "현재 실행"이 구분되지 않는 회색 지대에 있다.

필수 안전 베이스라인 지금 반드시 있어야 함. 이것 없이 Phase 시작 불가. Phase 1 진입 전 완료.
가설적 자동화 유용할 것 같아 설계됨. 실제 반복 패턴이 관찰되면 채택. 관찰 없이 도입하지 않음.
관찰 후 채택 이미 관찰됐고 채택됨. 규약 개정을 통해 정식 도입된 항목.
설계만 · 미도입 개념적으로만 존재. 아직 파일도 만들지 않음. 미래 Phase의 진입 조건 충족 시 검토.

2.1상태 이동의 원칙

상태는 한 방향으로만 이동한다.

설계만 → 가설적 자동화 → 관찰 후 채택. 역방향은 없다. 가설이 관찰로 검증되지 못하면 폐기되지 다시 설계만으로 되돌아가지 않는다. 이 원칙이 있어야 문서가 무한히 부풀지 않는다.

필수 안전 베이스라인은 별도 라인이다. 이것은 Phase 시작 전에 반드시 있어야 하는 것들이며 관찰 대상이 아니다. 관찰의 전제 조건.

2.2왜 이 구분이 필요한가

구분이 없으면 두 종류의 실패가 발생한다.

  • 미래 설계의 현재 도입. "언젠가 필요할 것"이 지금 만들어진다. Phase 1에 15개 파일이 있는 상태.
  • 필수의 관찰 후 도입 미룸. 진짜 필수(권한 강제, PR 템플릿)를 "관찰 후 채택"으로 미룬다. 안전 없이 실행이 시작되는 상태.

네 상태의 명시는 이 두 실패를 방지한다.

3.1Phase 1 시작에 필요한 것

위 트리에서 필수 뱃지가 붙은 5개만 있으면 Phase 1이 시작된다.

  • CLAUDE.md — 지침 층
  • .claude/settings.json — 강제 층 (권한)
  • .claude/hooks/guard-command.sh — 강제 층 (위험 명령)
  • .github/pull_request_template.md — 관찰 층 (근거 필드)
  • .github/workflows/ci.yml — 결정적 검증

기존 baseline의 pr-review.yml, baseline-diagnose.yml, orchestrator/*는 이미 있으므로 별도 추가 없음.

가설 뱃지가 붙은 것들(validate-write-scope.sh, CODEOWNERS, ISSUE_TEMPLATE, docs/*)은 Phase 1에서 관찰이 그것들의 필요를 정당화하면 추가된다. 첫 5~10개 PR을 처리하며 어떤 위반이 자주 발생하는지, 어떤 정보가 자주 누락되는지를 봐야 이것들의 정확한 모양이 정해진다.

설계만 뱃지가 붙은 것들은 Phase 2·3의 진입 조건이 충족될 때 별도 판단으로 추가된다.

§ 04 — Delegation Contract Realization

위임 계약의 실체화 지점

개념서 위임 계약의 세 성분이 이 프로젝트의 어떤 파일에 실체화되는가.

개념서 R2와 명세서 R3에서 위임 계약은 이 프로젝트의 최상위 원칙이다. 이 계약이 추상 개념에 머무르지 않으려면 파일에 실체화되어야 한다.

Phase 1에서 실체화되지 않는 것

변경 가능 범위(validate-write-scope.sh)와 금지 조건의 강제(CODEOWNERS)는 Phase 1에서 가설 상태다. 관찰 후 정확한 모양이 정해진다. 이 두 항목이 Phase 1 진행 중 필요하다고 판명되면 즉시 승격된다.

§ 08 — Policy vs Implementation

원칙과 구현의 분리

각 자동화를 원칙 · 현 구현 · 대안 3단으로 표기한다. 도구가 바뀌어도 원칙이 흔들리지 않는다.

이 프로젝트의 자동화는 특정 도구에 강하게 결합되어 있다. Claude Code · GitHub Actions · Anthropic API. 하지만 원칙은 도구가 아니다. 원칙과 구현을 분리해 표기하면 나중에 도구를 바꿔도 원칙이 유지된다.

8.1주요 자동화의 정책 · 구현 · 대안

위험 명령 실행 전 차단

Policy
위험한 shell 명령은 실행 전에 결정적으로 차단된다.
Implementation
Claude Code의 PreToolUse hook + .claude/settings.json의 deny 배열
Alternatives
Shell wrapper CLI · Container seccomp profile · CI runner permission scope · 별도 sandbox 실행기

편집 범위 제한

Policy
에이전트의 파일 편집이 위임 계약의 변경 범위를 벗어나지 못한다.
Implementation
Claude Code의 PreToolUse hook (validate-write-scope.sh)
Alternatives
Git worktree 격리 · 파일시스템 read-only 마운트 · Container에서 volume 제한 · CI에서 patch 범위 검증

민감 파일 승인 강제

Policy
민감 파일 변경은 별도 승인 없이 머지되지 않는다.
Implementation
GitHub CODEOWNERS + Branch Protection의 CODEOWNERS 승인 필수 설정
Alternatives
GitLab의 approval rules · Bitbucket의 default reviewer · 커스텀 pre-merge check · 별도 리뷰 봇

결정적 검증이 AI 리뷰보다 먼저

Policy
기계가 찾을 수 있는 오류는 기계가 먼저 제거한다. AI 리뷰는 결정적 검증 통과 후에만.
Implementation
GitHub Actions의 workflow needs: 종속성. pr-review.yml이 ci.yml에 needs.
Alternatives
CircleCI workflow orchestration · Jenkins pipeline stage · 별도 orchestrator가 순서 관리

인프라 apply의 사람 게이트

Policy
인프라 변경은 사람이 명시적으로 apply 트리거한다. 자동 apply 금지.
Implementation
GitHub Actions workflow_dispatch only + GitHub Environments 보호 규칙
Alternatives
Atlantis의 PR comment apply · Terraform Cloud의 manual apply · 별도 CD 도구의 approval gate
분리 표기의 이득

이 3단 표기가 있으면 도구 이전이 원칙 재설계로 오인되지 않는다. 예를 들어 Claude Code를 다른 도구로 바꿔도 원칙은 그대로다. 구현란만 갱신하면 된다. 이것이 개념서 R2의 명제 XII(원칙과 구현의 분리)가 청사진에 실체화된 모습이다.

§ 10 — Phase 1 Scenario

Phase 1 축소 시나리오

필수 5개로 시작하는 얇은 Phase 1. R1의 절반 규모.

Phase 01 · Reduced 파이프라인 증명 · 관찰이 산출물 Week 1~3

목표: 최소 안전 위에서 3~5개 실제 PR 흐름. 반복 패턴 관찰. 관찰 없이는 다음 자동화 추가 없음.

완료 조건: 필수 5개가 실제로 작동. 3~5개 PR 처리. 반복 패턴이 실제로 관찰됨. 관찰이 규약 개정으로 이어진 사례 1건 이상. Phase 2 진입 조건 충족.

10.2Week 1~2 · 첫 변환 사이클

  1. 이슈 확인 — gh issue view로 상세 확인. 위임 계약 성분이 이슈 본문에 채워져 있는지 확인.
  2. 브랜치 생성 — git checkout -b chore/auth-dockerfile-multistage
  3. Claude Code 편집 — claude 실행. 이슈 참조 지시. settings.json + guard-command.sh가 강제 층으로 작동.
  4. 강제 층 관찰 — 위험 명령 시도 시 실제로 차단됨을 확인. 지침이 실효를 갖는 첫 순간.
  5. 검증 · 커밋 · 푸시 — 로컬에서 npm test 통과 확인 후 push.
  6. PR 생성 — gh pr create. PR 템플릿 강제 필드 채우기. 5축 판정과 미검증 사항이 명시적으로.
  7. ci.yml 실행 — 결정적 검증이 먼저. 통과하면 pr-review.yml.
  8. 자동 리뷰 — 1~2분 내 리뷰 코멘트. 판단 관찰 가능성 층의 첫 축적.
  9. 사람 검토 — 저인지부하 게이트. 위험 등급 · 미검증 사항 · 롤백만 확인. R0이면 2분, R1이면 8분 이내.
  10. 머지 — Merge. Closes #N으로 이슈 자동 닫힘.
  11. 관찰 기록 — 이 사이클에서 무엇이 관찰됐는지 짧게 정리. 어떤 지침이 잘 지켜졌고 무엇이 자주 잘못됐는가.

10.3Week 2~3 · 반복과 관찰의 축적

같은 사이클을 3~5회 반복. 각 사이클마다 다음을 관찰한다. 이 관찰이 Phase 1의 진짜 산출물이다.

  • 어떤 명령이 자주 ask로 판정되는가 — 이것들이 allow로 옮겨질 후보가 있는지
  • 어떤 편집이 위임 계약을 벗어나려 하는가 — validate-write-scope.sh의 도입 근거가 되는가
  • 어떤 정보가 이슈 본문에서 자주 누락되는가 — ISSUE_TEMPLATE의 필수 필드가 될 후보
  • 어떤 파일이 잘못 변경되려 하는가 — CODEOWNERS의 대상이 될 후보
  • 자동 리뷰가 무엇을 찾고 무엇을 놓치는가 — 채택률과 허위 양성률
  • 중단 조건이 실제로 트리거되는가 — 조건이 예민한가 둔감한가

10.4Week 3 · 첫 학습 회로 실행

Phase 1 종료 전 최소 1건의 학습 회로가 완결되어야 한다. 관찰이 규약 개정으로 이어지고 그 개정이 실제로 반영된 사례. 예:

"Phase 1 관찰: 3개 사이클에서 에이전트가 package.json을 함께 편집하려 함. 이것이 편집 범위 초과인가? 관찰 후 판단: 의존성 변경 없이 편집되는 경우는 metadata 변경뿐이므로 허용. 규약 개정: CLAUDE.md에 이 예외를 명시. 이후 관찰: 같은 상황에서 재차 개입 필요 없음."

이 사례가 축적되어야 Phase 2 진입 조건이 충족된다. § 13에서 학습 회로 실행이 더 자세히 다뤄진다.

  1. 이슈 등록 — gh issue create. ISSUE_TEMPLATE 사용 (Phase 1 관찰이 채운 필수 필드).
  2. spec-lint 실행 — 자동. 필수 필드 · 모호 표현 · 정량 수용 조건 확인. 통과하면 자동 spec-lint-passed 라벨.
  3. risk-classify 실행 — 자동. 5축 판정. risk:R1 등의 라벨 부착.
  4. spec-ready 게이트 — 사람이 검토. 이 스펙이 위임 가능한 상태인지 최종 판단. 통과하면 spec-ready 라벨.
  5. ready-for-draft 라벨 — 사람이 부착. code-draft.yml 트리거.
  6. 자동 흐름 시작 — 브랜치 생성 · Claude Code 헤드리스 코드 초안 · 커밋 · PR 오픈.
  7. ci.yml 실행 — 결정적 검증 먼저.
  8. pr-review.yml + security.yml 병렬 — 두 리뷰 결과가 별도 코멘트.
  9. 사람 검토 — 저인지부하 게이트. 위험 등급에 비례한 시간.
  10. 머지 — 만족 시 Merge.

12.1진입 조건

  • Phase 2 코드 변환 2건 이상 성공적 완결

12.2Merge와 Apply의 분리

Phase 3의 결정적 차이. Merge = plan 승인, Apply = 실제 인프라 변경. 두 개의 서로 다른 사람 게이트.

  1. 이슈 — label: phase-3,infra,ready-for-draft
  2. 자동 코드 생성 — Terraform 모듈 초안 · PR 오픈
  3. 병렬 리뷰 — pr-review (코드) + terraform-plan (인프라). Plan 결과에 Claude가 리스크·비용 요약 별도 코멘트.
  4. Plan 검토 — 추가·변경·삭제 리소스, 월 예상 비용, 리스크 확인
  5. Merge (게이트 1) — 코드가 옳다는 승인. 실제 인프라는 아직 변경 안 됨.
  6. Apply 트리거 (게이트 2) — gh workflow run terraform-apply.yml --field environment=dev. 사람이 명시적 실행.
  7. Dev 검증 — Grafana 대시보드 · 통합 테스트. 문제 없으면 staging.
  8. Staging apply — 24시간 관측 창 후 prod.
  9. Prod apply — 배포 창 조율. 실시간 관측 강화. 문제 시 즉시 롤백.
Apply 게이트 원칙

Apply는 어떤 상황에서도 자동 트리거 금지. 이유는 개념서 R2의 명제 III(다차원 위험 판정) — 인프라 변경은 partial reversibility에 blast_radius가 infra고 detectability가 mixed다. Claude가 plan 해석을 제공하지만 apply 결정은 조직 맥락(배포 창 · 트래픽 · 다른 진행 작업)을 아는 사람만 할 수 있다.

  • reviewer.md 서브에이전트 도입 — 컨텍스트 격리. 구현자 self-report 미제공.
  • 반례 탐색 지시 — reviewer에 명시적으로 반례를 찾도록 프롬프트.
  • 다른 모델 계열 검토 — 특히 R3 변경은 Opus 아닌 다른 계열로 이중 검증 (Phase 3 후반).

§ 13 — Learning Loop Execution

학습 회로 시나리오

관찰이 규약 개정으로 이어지는 실제 흐름. 개념서 명제 X의 실체화.

학습 회로는 문서에만 존재하면 학습이 아니다. 이 프로젝트에서 학습 회로는 다음 시나리오처럼 정기 흐름으로 작동한다.

13.1주간 학습 회로 (Phase 1~2)

Weekly Loop · 주 1회 실행
1 관찰 수집한 주 동안의 회수 이벤트 · 강제 층 차단 · 자동 리뷰 finding · revert · 사람 개입 로그를 스크립트로 집계.
2 패턴 발견Claude API로 로그 분석. 반복 3회 이상의 이슈 유형 · 자주 위반되는 지침 · 자주 놓치는 리뷰 카테고리 추출.
3 개정 제안 이슈 생성발견된 패턴마다 type: rule-amendment 라벨의 이슈 자동 생성. 어느 파일의 어느 부분을 어떻게 개정할지 명시.
4 사람 검토제안 이슈 중 채택할 것 선정. 대부분 rejeted or 수정 필요. 채택된 것만 ready-for-draft로 승격.
5 개정 PR 생성일반 사이클과 동일. code-draft.yml이 개정 PR 생성. 이 PR을 현재 규약을 따르는 자동 리뷰가 검토 — 재귀 자기 검증.
6 머지와 적용새 규약이 지침 층과 강제 층에 반영. 이후 세션부터 새 규약 적용.
7 다음 주 검증다음 주 관찰에서 개정된 규약이 실제로 반복 실패를 줄였는지 확인. 안 줄었으면 회로 재실행.

13.2학습 회로의 실제 예시

가상의 첫 학습 회로

관찰: Phase 1 3주간 5회의 PR에서 에이전트가 package.json 편집을 시도. 그중 3회는 dependency 변경 시도(위험), 2회는 script name 오타 수정(무해).

패턴: package.json이 다목적 파일이라 편집 범위 강제만으로는 부적절.

개정 제안: validate-write-scope.sh에 특수 규칙 추가 — package.json 편집 시 diff 내용 검사. dependency 관련 라인 변경이면 ask, script/metadata만 변경이면 allow.

재귀 검토: 이 제안 PR을 현재 규약이 리뷰. 규약과 정합적인지, 강제 층 자기 검증 질문("이 원칙이 지켜지지 않아도 아무 일이 안 일어나는가")을 통과하는지 확인.

결과: 머지 후 다음 주 관찰에서 package.json 관련 개입이 3회 → 0회로 감소. 학습 회로 완결.

13.3학습이 없는 상태의 신호

학습 회로가 형식만 남고 실질이 없는 상태의 신호는 다음이다.

  • 같은 지시를 사람이 계속 반복한다. "이 부분은 손대지 마라"를 매번 이슈에 써야 한다면 그것은 규약이 되어야 하는 신호.
  • 규약 개정이 없다. Phase 진행 중 몇 주간 CLAUDE.md나 settings.json에 커밋이 없다면 학습이 정지된 상태.
  • 같은 유형의 revert가 반복된다. 특정 카테고리 실패가 반복되는데 규약에 반영이 없다면 회로가 끊겨 있다.
§ 14 — Metrics by Grade

지표 · 위험 등급별 세분화

R0~R3 각각 다른 기대치. 단일 지표의 함정을 피한다.

R1에서 지표를 단일 값으로 목표했다. R2에서는 위험 등급별로 세분화한다. 같은 지표가 R0에서는 너무 길고 R3에서는 너무 짧을 수 있다.

14.5학습 지표

  • 같은 유형 실패의 시간별 감소 — 학습 회로가 실제 작동하는지
  • 사람 반복 지시 감소 — 규약이 프로젝트 패턴을 흡수하는지
  • 규약 개정 근거의 관찰 추적률 — 개정이 즉흥적이지 않은지
  • 주간 회로 완결률 — 회로가 실제로 돌고 있는지
지표의 원칙

§ 15 — Failure Playbook

실패 플레이북

중단 조건 발동 · 잘못된 자동 판단 · revert 필요 시의 대응 절차.

15.1중단 조건 발동 (Spec R3 § 12 참조)

상황즉시 조치후속 조치
같은 테스트 2회 실패자동 재시도 중단. 러너 종료이슈에 실패 원인 후보·시도·선택지 코멘트. 인계 패킷 출력
수정 루프 2회 초과브랜치에 needs-human-review 라벨사람이 로컬 Claude Code로 개입
변경 파일 상한 초과단계적: 경고 → 재승인 → 중단이슈를 서브 이슈들로 분할
테스트 삭제·약화 시도훅에서 즉시 차단사람 개입 필수. 왜 이 테스트가 문제인지 이슈 등록
보안·권한 영역 진입settings.json 차단R3 이슈로 별도 등록. Phase 3 사이클로 처리

15.2Revert 절차

  1. 즉시 revert — git revert <merge-commit>. main에 revert 커밋 생성.
  2. Revert PR도 자동 리뷰 — 이 리뷰가 규약을 따르는지 확인.
  3. 원인 분석 이슈 — 왜 이 변경이 문제였는지, 자동 리뷰가 왜 놓쳤는지 별도 이슈로.
  4. 학습 회로 트리거 — 이 revert가 반복 패턴이면 규약 개정 제안으로 승격.
  5. 지표 기록 — revert 비율 · change failure rate · rollback latency에 반영.

15.3인프라 Apply 실패 (Phase 3)

  1. 자동 롤백 워크플로 — terraform-apply.yml 실패 감지 시 이전 상태로 되돌리는 로직 실행.
  2. 영향 범위 확인 — Grafana · 통합 테스트로 사용자 영향 판단.
  3. 이슈 등록 — 실패 원인 · 시도한 것 · 영향을 상세 기록.
  4. Prod 재시도 판단 — 사람이 조직 맥락 고려해 다음 배포 창 결정.

15.4학습 회로 실패

학습 회로가 정지된 상태(§ 13.3 신호)가 감지되면 다음을 수행한다.

  • Phase 진행 일시 중단. 새 사이클 시작 전 회로를 되살린다.
  • 회고 조기 소환. Phase 종료를 기다리지 않고 지금 관찰된 것 정리.
  • 규약 개정 우선순위. 반복 관찰된 실패를 규약에 반영하기 전에는 새 자동화 추가 없음.
플레이북의 원칙

실패는 시스템 결함이 아니라 시스템이 자기 한계를 인식했다는 증거다. 중단 조건이 작동한다는 것은 자동화가 성숙했다는 뜻. 실패 없이 계속 진행되는 자동화가 오히려 위험 신호다.
