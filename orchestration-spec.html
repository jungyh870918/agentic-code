Rev. R3 Orchestration Specification agentic-ticketing

에이전트 오케스트레이션 명세

이 문서는 agentic-ticketing 프로젝트의 헌법이다. 개념서 R2의 열두 명제를 이 프로젝트의 맥락에 실체화하고, 실행 청사진이 참조하는 규약의 최상위 원본을 제공한다. 개념서가 도구 독립적인 원리를 다룬다면 이 명세서는 이 특정 프로젝트에서 그 원리가 어떤 모양으로 실체화되는지를 다룬다.

R3 개정 — 근본 재구성

R2의 정적 6축 거버넌스 모델을 폐기하고 개념서 R2의 위임 계약 모델로 재구성한다. R2의 "권한 층 · 신뢰 경계 · 가역성 · 관찰 · 에스컬레이션 · 상태분리" 여섯 축은 개념서 R2의 열두 명제에 흡수되어 재배치된다.

주요 변경: 정적 권한 층 → 위임 계약, 단일 가역성 → 다차원 위험 판정, 1초 게이트 → 저인지부하 게이트, 단층 관찰 → 두 층 관찰. 그리고 세 개의 새 원칙(스펙 준비도, 독립 검증, 학습 회로)이 도입된다.

§ 01 — Preamble

프리앰블

이 명세서가 무엇이고 무엇이 아닌지, 그리고 왜 R3로 재구성되었는지.

1.1이 문서의 성격

이 명세서는 agentic-ticketing 프로젝트의 최상위 규약이다. 프로젝트에서 이루어지는 모든 자동화 판단이 궁극적으로 이 문서를 참조한다. 하위 문서(CLAUDE.md, ADR, docs/agentic-development/*)는 이 명세서에 종속되며, 이 명세서와 충돌하면 이 명세서가 우선한다.

이 명세서는 매뉴얼이 아니다. 도구 사용법, 명령 시퀀스, 파일 예시는 이 문서에 담기지 않는다. 그것들은 실행 청사진이 담당한다. 이 명세서는 왜 이 프로젝트가 이런 모양이어야 하는지와 이 프로젝트에서 개념이 어떻게 실체화되는지만 다룬다.

1.2세 문서의 관계

이 프로젝트에는 세 문서가 축을 이룬다.

개념서 R2
왜를 다룬다. 열두 명제로 구성된 도구 독립적 원리서. 프로젝트가 바뀌어도 유지된다.
명세서 R3
무엇을 다룬다. 개념을 이 프로젝트에 실체화한 헌법. 이 문서.
청사진 R2
어떻게를 다룬다. 파일 · 시나리오 · 확장 순서. 실행 지도.

세 문서는 서로 참조하지만 성격이 다르다. 개념서가 개정되면 명세서와 청사진이 그것에 정합하도록 개정되고, 명세서가 개정되면 청사진이 정합하도록 개정된다. 청사진의 개정은 앞의 두 문서에 영향을 주지 않는다.

1.3R2에서 R3으로의 변화

R2 명세서는 여섯 개의 거버넌스 축(권한·신뢰경계·가역성·관찰·에스컬레이션·상태분리)에 기반해 있었다. 이 여섯 축은 개별적으로는 유용한 통찰이지만 다음의 한계가 있었다.

  • 정적 권한 층이 실제 개발을 부정확하게 표현했다. "판단은 사람, 실행은 에이전트"의 이분법이 실제 위임되는 판단의 범위를 흐렸다.
  • 가역성이 위험의 유일한 축으로 사용됐다. 파급 범위, 감지 가능성, 데이터 민감도 같은 다른 축이 무시됐다.
  • 관찰 가능성이 행위 기록에 머물렀다. 판단의 전제와 대안을 남기는 층이 없었다.
  • 학습 회로가 부재했다. 관찰이 규약 개정으로 이어지는 순환이 명시되지 않았다.
  • 스펙 준비도 개념이 부재했다. 코드 이전에 문제 정의를 검증하는 게이트가 없었다.
  • 독립 검증 원칙이 부재했다. 같은 컨텍스트를 공유하는 자기 확인이 검증으로 오인될 수 있었다.

R3는 개념서 R2의 열두 명제를 축으로 삼아 이 한계들에 대응한다.

§ 02 — Project Identity

프로젝트 정체성

agentic-ticketing이 무엇을 증명하려 하는가.

2.1산출물의 정의

이 프로젝트의 산출물은 앱이 아니라 사람과 에이전트가 협업하는 방식에 대한 결정들의 실체화다. 앱(ticketing 마이크로서비스)은 이 결정들을 검증하는 실험대일 뿐이다. 앱을 개선하는 것이 목적이 아니라 앱을 개선하는 과정이 목적이다.

2.2증명 대상 — 재정의

R2에서는 증명 대상을 "프로세스 추적 가능성"이라고 표현했다. R3에서는 이것을 더 정확히 재정의한다. 이 프로젝트가 증명하려는 것은 네 가지다.

증명 대상 1 · 생산성

동일 유형 작업의 리드 타임 감소

사람이 실제로 키보드에서 손을 뗀 시간

감독 비용 증가 없이 얻어진 순수 절감

증명 대상 2 · 품질

Escaped defect의 증가 없음

테스트가 형식이 아닌 실질로 추가됨

변경이 요구사항을 실제로 충족

증명 대상 3 · 통제

위험 행동이 실제로 차단됨

차단을 우회할 수 없음

에이전트가 위임 계약의 경계를 이해

증명 대상 4 · 학습

반복 실패가 규약 개선으로 이어짐

같은 지시를 반복할 필요가 감소

프로젝트 고유 패턴이 규약에 흡수됨

R2에서 강조된 추적 가능성은 증명 대상 3의 한 요소로 흡수된다. 통제와 감사만으로는 이 프로젝트의 성공을 판정할 수 없다는 것이 R3의 재정의다.

2.3베이스라인의 역할

Stephen Grider의 ticketing 강의 결과물이 베이스라인이다. 이 코드를 새로 만드는 것이 아니라 이미 완성된 코드에 점진적 변환을 가하며 위임 계약과 학습 회로를 검증한다.

베이스라인은 손대지 말 영역이 있다. 비즈니스 로직 자체는 변환 대상이 아니다. 변환 가능한 영역은 인프라, 의존성, 타입, 테스트, 미들웨어, 배포 코드다. 이 구분이 흐려지면 프로젝트가 앱 개발이 되어버린다.

산출물은 앱이 아니라 협업의 결정이다. 앱은 그 결정을 검증하는 실험대일 뿐이다.

§ 03 — Delegation Contract

위임 계약

이 프로젝트의 최상위 원칙. 사람과 에이전트의 관계를 매 작업마다 명시하는 계약.

3.1계약의 세 성분

모든 작업은 위임 계약을 갖는다. 계약은 세 성분으로 구성된다.

Delegation Contract · agentic-ticketing Per-task
사람이 정의
  • 목표 — 이 작업의 달성 대상. 이슈 제목·본문에 명시.
  • 수용 조건 — 완료를 판정하는 기준. 이슈 템플릿의 필수 필드.
  • 금지 조건 — 손대지 말 영역. 이슈 본문에 명시하거나 CODEOWNERS가 강제.
  • 변경 가능 범위 — 편집 허용 파일·모듈. .claude/hooks/validate-write-scope.sh가 강제.
  • 예산 — 시간·토큰·복잡도의 상한. 러너 timeout과 diff size limit로 실체화.
  • 검증 기준 — 통과해야 할 결정적 검사. ci.yml이 담당.
  • 에스컬레이션 조건 — 회수 트리거. CLAUDE.md에 정량 명시.
에이전트가 위임받음
  • 탐색 — 관련 코드·문서 조사. 읽기 권한 자유.
  • 국소 설계 판단 — 변경 범위 안에서 어떻게 만들지 결정.
  • 구현 — 실제 코드 작성. 편집 범위 강제 층 아래에서.
  • 검증 — 결정적 검사 실행과 해석.
  • 반례 탐색 — 구현의 실패 조건 검토.
  • 근거 제시 — 판단의 전제와 대안을 PR body에 남김.
사람에게 회수
  • 범위 확대 — 정의된 변경 범위 초과. 훅이 감지.
  • 불확실성 초과 — 확신도 임계치 아래.
  • 위험 등급 상승 — 다차원 판정이 계약 상단 초과.
  • 요구사항 충돌 — 목표와 금지 조건 모순 발견.
  • 비가역 작업 — 되돌릴 수 없는 결정 진입.
  • 학습되지 않은 패턴 — 규약이 다루지 않은 상황.

3.2계약이 명시되지 않은 상태의 위험

계약이 명시되지 않으면 두 종류의 상태가 발생한다.

  • 과대 위임. 목표만 주고 나머지를 에이전트가 알아서 결정한다. 사람은 자기가 무엇을 승인하고 있는지 모른 채 승인한다.
  • 과소 위임. 모든 판단을 사람이 반복한다. 에이전트가 자동완성 도구로 축소된다.

두 상태 모두 이 프로젝트가 증명하려는 것과 어긋난다. 계약이 명시적으로 매 작업마다 갱신되어야 한다.

3.3계약의 실체화 지점

이 프로젝트에서 위임 계약은 다음 파일들에 실체화된다.

계약 성분실체화 지점
목표 · 수용 조건 · 금지 영역.github/ISSUE_TEMPLATE/*.yml
변경 가능 범위.claude/hooks/validate-write-scope.sh
예산 (파일·diff 상한)Runner timeout · Diff size guard
검증 기준.github/workflows/ci.yml
에스컬레이션 조건CLAUDE.md · Hook logic
근거 제시 형식.github/pull_request_template.md

계약이 명시되지 않으면 관행이다. 관행은 조직마다 다르게 해석되고 시간이 지나면 잊혀진다.

§ 04 — Multi-axis Risk

다차원 위험 판정

위험은 다섯 축의 조합으로 판정되고, R0~R3는 사람에게 보이는 요약이다.

4.1다섯 축

이 프로젝트의 모든 위험 판정은 다음 다섯 축을 참조한다.

Blast Radius
파급 범위. file / module / service / cross-service / infra 중 하나.
Detectability
감지 가능성. 오류가 얼마나 빨리 드러나는가. high / mixed / delayed.
Reversibility
가역성. free / cost / partial / irreversible.
Data Sensitivity
데이터 민감도. public / internal / confidential / PII / financial.
Confidence
에이전트 확신도. 0.0 ~ 1.0. 에이전트가 스스로 신고.

이 다섯 축은 자동 리뷰와 훅이 참조하는 내부 판정 좌표다. 사람에게는 이 다섯 축의 조합이 R0~R3로 요약되어 보인다.

4.2등급 정의

R0 자동 처리 가능 후보

다섯 축이 모두 낮음. 문서, 포맷, 주석, 스냅샷 갱신, 정적 분석 자동 수정.

blast_radius · file detectability · high reversibility · free data_sensitivity · public
R1 일반 코드

파급이 서비스 내부에 머무르고 감지가 빠름. 내부 함수, UI 컴포넌트, 명확한 버그 수정, 테스트 추가.

blast_radius · module detectability · high reversibility · free · cost data_sensitivity · internal
R2 계약·데이터 영향

파급이 서비스 경계를 넘고 감지가 지연될 수 있음. API·이벤트 스키마, 공유 패키지, 캐싱, 동시성, 마이그레이션 초안.

blast_radius · cross-service detectability · mixed reversibility · partial data_sensitivity · internal · confidential
R3 고위험 — 하위 분류

인증·인가, 결제, 개인정보, 운영 DB, 프로덕션 클러스터, 시크릿, IAM, 파괴적 마이그레이션. R3 안에서도 변별이 필요하다.

R3-A · 승인 후 자동 실행 가능 (dev) R3-B · 이중 승인 + 스테이징 검증 R3-C · 사람 직접 실행 (prod) R3-D · 자동화 금지

4.3등급 판정 자동화

등급 판정은 scripts/classify-change.ts가 담당한다. 변경 파일 경로 · diff 크기 · 파일 성격을 조합해 5축을 산출하고, 5축이 R0~R3 요약 레이블을 도출한다. 판정 근거가 PR 코멘트에 자동 게시된다.

4.4판정의 원칙

  • 애매하면 상향. R1인지 R2인지 애매하면 R2. R2인지 R3인지 애매하면 R3.
  • 확신도가 낮으면 상향. 다른 축이 낮아도 confidence가 0.5 미만이면 한 단계 올린다.
  • 사람이 최종 판정을 오버라이드할 수 있다. 자동 판정이 낮게 나와도 사람이 등급을 올려 게이트를 강화할 수 있다. 반대(자동 판정보다 낮게)는 명시적 근거가 필요하다.
R2 → R3 상향의 함의

판정이 R3로 상향되면 자동 코드 생성이 중단되고 스펙 재검토 흐름으로 전환된다. R3는 에이전트가 초안과 분석만 담당하는 영역이므로 자동 생성 자체가 위임 계약 밖이다.

§ 05 — Low-Cognitive-Load Gate

저인지부하 게이트

사람 승인의 목표는 짧은 검토가 아니라 위험도에 비례한 검토를 낮은 인지 부하로 가능하게 하는 것.

5.1재정의

R2에서 사용했던 "1초 게이트" 표현은 폐기한다. 그 표현은 짧은 검토를 목표로 삼는 인상을 주었고, 실제로는 R0/R1에서만 가능한 상태를 일반 목표로 착각하게 만들었다.

R3에서 사람 게이트는 인지 부하를 위험도에 비례하게 유지하는 장치다. 시간이 아니라 근거의 밀도가 목표다.

5.2위험 등급별 검토 기대치

등급검토 시간 (중앙값)사람이 답하는 질문
R0< 2분변경이 정말 R0인가
R1< 8분구현이 목표를 실제로 달성하는가
R2< 20분계약 변경의 영향이 정확히 이해됐는가
R3시간 최소화 목표 없음이 결정이 지금 실행되어야 하는가

R3에서 검토가 빨리 끝난다는 것은 성숙도의 증거가 아니라 부실 검토의 신호다. 이 프로젝트는 R3 검토 시간을 단축하는 것을 목표로 삼지 않는다.

5.3사람이 답하는 두 질문

재정의된 게이트에서 사람이 답하는 질문은 두 가지다.

  • 제시된 근거가 충분한가. 에이전트가 정리한 전제 · 대안 · 위험 평가가 이 결정을 뒷받침하기에 충분한 밀도인가.
  • 변경이 수용 가능한가. 위임 계약의 범위 안에서 이 결정이 정당한가. 회수 조건을 어긋나게 하지 않는가.

승인의 시간을 줄이는 것이 아니라, 승인에 도달하는 인지 부하를 판단에 필요한 최소로 만드는 것.

§ 06 — Dual Enforcement

지침과 강제의 이중 구조

지침은 유도하고 규칙은 차단한다. 그리고 강제 층은 실행 주체마다 다르다.

6.1두 층의 성격

지침 층

에이전트가 읽는 문서. CLAUDE.md · 명세서 · 위임 계약 양식.

힘: "왜 이렇게 해야 하는가"를 전달. 규약에 없는 상황도 원칙으로 판단하게 함.

한계: 강제력 없음. 에이전트가 무시하거나 잘못 해석해도 막지 못함.

강제 층

실행 도구의 권한 설정과 훅. settings · hooks · CI · 브랜치 보호.

힘: 실효성 있음. 지침 해석과 무관하게 차단.

한계: 확장 어려움. 모든 상황을 규칙으로 열거할 수 없음.

6.2주체별 강제 층

R3의 중요한 세부. 강제 층은 하나가 아니다. 실행 주체마다 다른 강제 층이 있어야 한다.

실행 주체강제 층
로컬 Claude Code 세션.claude/settings.json + PreToolUse hooks
GitHub Actions 러너workflow permissions, GITHUB_TOKEN 스코프, environment protection
MCP 서버서버별 인증, tool-level permission, allowlist
Terraform / 클라우드 실행기IAM, workload identity, environment approval
Repository 자체Branch protection, CODEOWNERS, required checks

지침에 "운영 DB를 만지지 말라"고 쓰는 것과 실제로 로컬·CI·MCP 각각에서 운영 DB 접근이 차단되는 것은 다르다. 이 세부를 놓치면 지침은 있는데 강제는 반쪽인 상태가 된다.

6.3권한 강제의 자기 검증

이 프로젝트에서 새 규약을 만들 때 반드시 스스로에게 이 질문을 던진다.

Self-check

이 원칙이 지켜지지 않아도 아무 일이 일어나지 않는가? 답이 그렇다면 지침 층에만 존재하는 상태. 반드시 강제 층에 대응 규칙 추가. 어느 주체의 강제 층인지도 함께 명시.

6.4강제 층의 위반 처리

강제 층은 DENY / ASK / ALLOW로 판정한다. DENY는 실행 자체 차단. ASK는 사람에게 명시적 승인 요청. ALLOW는 자동 통과.

  • DENY 발동 시: 명령이 차단됐다는 로그가 남고, 에이전트는 위임 계약의 회수 조건 중 하나로 이 사건을 기록한다.
  • ASK 발동 시: 사람이 명시적으로 승인을 내리기 전까지 실행 대기. 시간 초과 시 자동 취소.
  • ALLOW 로그: 관찰 가능성 목적으로 모든 ALLOW도 기록. 사후 감사 가능.
§ 07 — Spec Readiness

스펙 준비도 게이트

가장 비싼 오류는 잘못된 코드가 아니라 잘못된 문제 정의. 코드 생성 이전에 판정한다.

7.1스펙 준비도의 정의

스펙 준비도는 이 이슈가 코드 생성에 충분히 명확한가를 판정하는 게이트다. 이 게이트가 통과되지 않으면 자동 코드 생성이 시작되지 않는다.

이 게이트는 위임 계약의 실체화와 동일하다. 계약이 채워지지 않았으면 위임 자체가 시작될 수 없다.

7.2준비도 판정 항목

  • 목표가 단일한가. 한 이슈에 여러 목표가 섞이면 분해 요청.
  • 수용 조건이 정량적인가. "잘 동작해야 한다"는 부적합. "테스트 X가 통과해야 한다"가 적합.
  • 수정 금지 영역이 정의되어 있는가. 손대지 말아야 할 파일·모듈이 명시.
  • 테스트 기대값이 있는가. 통과 조건이 명시.
  • 데이터 마이그레이션 여부가 있는가. 스키마·데이터를 건드리는지 명시.
  • API·이벤트 계약 변경 여부가 있는가. 경계 구역 변경 여부 명시.
  • 롤백 방법이 있는가. 실패 시 되돌리는 절차 명시.
  • 모호한 표현이 없는가. "적절히" · "가능하면" · "필요시" 같은 표현은 위임할 수 없음.

7.3흐름의 재배치

스펙 준비도 게이트가 추가되면 자동 흐름의 순서가 이렇게 된다.

# 이슈 생성부터 코드 생성까지의 흐름

Issue 등록
  ↓
spec-lint        # 준비도 자동 검사
  ↓ (필드가 채워짐)
risk-classify    # 5축 판정 → R0~R3 요약
  ↓
spec-ready       # 사람이 준비도 승인 (플랜 승인)
  ↓
ready-for-draft  # 여기서 처음 코드 생성 트리거
  ↓
Code draft → Verify → AI Review → Merge

R2에서는 ready-for-draft 라벨이 곧바로 코드 생성 트리거였다. R3에서는 spec-ready와 ready-for-draft가 두 개의 서로 다른 게이트다. 전자는 스펙이 위임 가능한 상태임을 승인하는 게이트, 후자는 코드 생성을 시작하는 신호.

7.4준비도의 자동 검사와 사람 승인

준비도 검사는 두 층으로 구성된다.

  • 자동 lint. 이슈 템플릿의 필수 필드가 채워졌는지, 모호한 표현이 있는지, 정량적 수용 조건이 있는지 자동 검사.
  • 사람 승인. lint 통과 후 사람이 최종 승인. 자동 lint가 잡지 못한 스펙의 의미 결함을 사람이 잡음.

준비되지 않은 스펙에 코드 생성을 위임하면, 잘 짜인 잘못된 코드가 나온다. 이것이 이 프로젝트에서 가장 저렴하게 방지할 수 있는 실패다.

§ 08 — Independent Verification

독립 검증 구조

리뷰가 자기 확인이 되지 않도록 컨텍스트를 격리한다.

8.1왜 컨텍스트 격리가 필요한가

구현자와 리뷰어가 다음을 공유하면 이미 독립이 아니다.

  • 같은 규약 문서를 시스템 프롬프트로 읽는다.
  • 같은 언어 모델을 호출한다.
  • 같은 diff와 설명을 본다.
  • 구현자가 작성한 판단 근거를 리뷰어가 그대로 읽는다.

이 상태에서 리뷰어는 구현자의 세계관을 그대로 물려받는다. 구현자가 놓친 것을 리뷰어도 놓친다.

8.2이 프로젝트의 독립 검증 강도

강도구성도입 시점
약한 독립컨텍스트만 격리. 같은 모델, 같은 규약. 리뷰어는 구현자의 self-report 미제공.Phase 1 도입
중간 독립컨텍스트 격리 + 프롬프트 다양화. 리뷰어에 반례 탐색을 명시적으로 지시.Phase 2 도입
강한 독립컨텍스트 격리 + 다른 모델 계열. 상관관계 낮은 오류를 서로 잡음.Phase 3 검토

Phase 1에서 도입되는 것은 약한 독립이다. 이 사실을 명시적으로 인정한다. 진정한 독립 검증이 아님을 알고 그에 맞는 기대치를 유지한다.

8.3리뷰어에게 제공하는 것과 제공하지 않는 것

제공

원 이슈 본문

수용 조건

수정 금지 영역

변경 diff

결정적 검증 결과 (테스트·타입·린트)

비제공

구현자의 자기 설명

구현자의 판단 근거

이전 리뷰 결론

구현 과정의 대화 로그

8.4결정적 검증이 먼저다

독립 검증이 어렵다는 사실은 결정적 검증의 중요성을 재강조한다. 컴파일러 · 타입 시스템 · 테스트 러너의 판정은 언어 모델과 완전히 독립적이다. 기계가 찾을 수 있는 오류는 기계가 먼저 잡아야 한다.

이 프로젝트에서 자동 리뷰(AI Review)는 결정적 검증 이후에 실행된다. 결정적 검증이 실패한 상태에서 AI 리뷰를 실행하는 것은 토큰 낭비이자 노이즈 증가다.

진짜 독립 검증은 값비싸다. 그래서 결정적 검증을 먼저 최대화하고, 남은 부분에만 언어 모델 리뷰를 얹는다.

§ 09 — Observability

두 층의 관찰 가능성

무엇을 했는가와 왜 그렇게 판단했는가는 다른 종류의 흔적.

9.1행위 관찰 가능성

첫 번째 층. 무엇을 했는가의 기록.

  • 어떤 명령을 실행했는가
  • 어떤 파일을 수정했는가
  • 어떤 API를 호출했는가
  • 얼마나 걸렸는가
  • 얼마나 비용이 들었는가

이 층은 자동 수집된다. Git 이력, GitHub 상태, CI artifact, 러너 로그가 담당한다. 대부분의 관찰 가능성 논의가 이 층에서 멈춘다.

9.2판단 관찰 가능성

두 번째 층. 왜 그렇게 판단했는가의 기록.

  • 어떤 전제를 사용했는가. 이 판단이 어떤 가정 위에 세워졌는가.
  • 어떤 대안을 제외했는가. 다른 선택지들이 왜 채택되지 않았는가.
  • 무엇을 알지 못했는가. 이 판단에서 확신할 수 없었던 부분이 무엇인가.
  • 판단의 확신도는 얼마인가. 에이전트가 스스로 얼마나 신뢰하는가.
  • 어떤 증거가 반증하면 판단이 바뀌는가. 이 판단이 뒤집힐 조건이 무엇인가.

9.3이 프로젝트에서 두 층의 실체화

층실체화 지점
행위 관찰Git commit history · CI logs · Actions artifacts · .agent-runs/*.json
판단 관찰PR body의 근거 섹션 · 리뷰 코멘트의 전제·대안 서술 · ADR

9.4기록의 밀도 요구

판단 관찰 가능성은 정보의 양이 아니라 정보의 밀도다. 에이전트가 페이지를 채우는 rationale을 남겨도 그것이 전제 · 대안 · 불확실성을 담지 않으면 판단 흔적이 없다.

PR 템플릿의 필수 필드는 이 밀도를 강제한다. "변경하지 않은 범위" "미검증 사항" "롤백 방법" "위험 등급 · 5축 판정"이 그 실체다.

R2 대비 변화

R2 명세서에서 관찰 가능성은 "GitHub에 흔적이 남는다"에 머물렀다. R3는 이를 두 층으로 분리하고 판단 관찰 가능성이 사후 학습의 재료임을 명시한다. 다음 § 11의 학습 회로가 이 층을 원료로 삼는다.

§ 10 — Trust & Delegation Expansion

신뢰 축적과 위임 확장

확장되는 것은 자동화의 총량이 아니라 위임 계약의 범위와 정교함.

10.1Phase 로드맵의 재정의

R2에서 Phase 로드맵은 "자동화가 확장되는 여정"으로 표현됐다. R3에서 이 표현을 수정한다. Phase는 위임 계약의 범위가 확장되는 여정이다.

Phase기간계약 상태
Phase 12~3주사람이 계약의 모든 항목 명시. 에이전트는 좁게 위임받음. 관찰이 산출물.
Phase 23~4주관찰된 반복 패턴이 계약 기본값으로 승격. 사람은 목표와 예외만 정의.
Phase 34~6주고위험 영역이 위임 안으로 들어오면서 회수 조건이 새로 강화. 위임 확장과 게이트 재배치가 동시에.

10.2Phase 이동의 판정 기준

Phase 이동은 시간이 아니라 신뢰 축적이 결정한다. 다음 조건이 관찰되면 다음 Phase로 이동을 검토한다.

Phase 1 → Phase 2 이동 조건

10~20개 PR 처리. AI finding 채택률 > 40%. Revert 비율 ≤ 5%. 중단 조건이 최소 1~2회 실제로 작동. 관찰이 규약 개정으로 이어진 사례 1건 이상.

Phase 2 → Phase 3 이동 조건

Phase 2의 코드 변환 2건 이상 성공적 완결. 자동 코드 생성 revert 비율 ≤ 5%. 보안 스캔 통합 안정. ADR 최소 3개 축적. 학습 회로 1개 이상 완료.

10.3왜 처음부터 넓게 위임하지 않는가

세 가지 이유가 있다.

  • 계약의 기본값이 검증되지 않은 상태다. 어떤 판단을 위임할 수 있고 어떤 판단은 사람이 해야 하는지, 조직 맥락에서 검증되기 전에는 알 수 없다.
  • 회수 조건이 미숙하다. 어떤 신호가 진짜 회수 트리거인지는 실제 실패 사례를 관찰해야 정해진다.
  • 도입은 눈에 보이는 신뢰를 요구한다. 첫 단계에서 축적한 관찰 기록이 신뢰의 근거다.

자동화의 총량은 성숙도의 지표가 아니다. 위임 계약의 정교함과 회수 조건의 정확성이 성숙도다.

§ 11 — Learning Loop

학습 회로

관찰이 규약 개정으로 이어져야 시스템이 학습한다.

11.1왜 학습 회로가 명시되어야 하는가

관찰 기록이 쌓인다는 것과 시스템이 학습한다는 것은 다르다. 실패 로그를 사람이 읽고, 패턴을 발견하고, 규약을 개정하고, 그 개정이 다시 에이전트의 행동을 바꿔야 학습이다.

학습 회로가 명시되지 않으면 시스템은 정교한 자동완성에 머문다. 같은 실패가 반복되고, 사람이 같은 지시를 반복한다.

11.2이 프로젝트의 학습 회로

규약 개정 회로 · Feedback Loop
1 관찰실패 · 회수 · 예외 · 사람 개입이 판단 관찰 가능성 층에 기록.
2 패턴 발견주 1회 정기 검토. 반복되는 회수 조건, 자주 위반되는 지침, 자주 놓치는 리뷰 유형 파악.
3 개정 제안패턴이 규약의 어떤 부분을 어떻게 개정해야 하는지 명시된 제안. ADR로 등록.
4 재귀 리뷰제안 PR이 현재 살아있는 규약을 따르는 에이전트에 의해 리뷰. 자기 다음 버전을 자기 현재 원칙으로 검증.
5 적용개정된 규약이 지침 층과 강제 층 모두에 반영. 이 시점 이후 모든 자동 행동이 새 규약을 따름.
6 회고개정이 실제로 반복 실패를 줄였는지 검증. Phase 종료 시 회고 문서로 갈무리.

11.3학습의 지표

시스템이 학습하고 있는지의 지표는 다음이다.

  • 같은 유형의 실패가 시간에 따라 감소하는가.
  • 사람이 같은 지시를 반복하는 빈도가 감소하는가.
  • 규약 개정의 근거가 관찰 기록으로 추적 가능한가.
  • 개정된 규약이 실제로 관찰된 문제를 줄이는가.

관찰이 규약 개정으로 이어지는 회로가 없으면 시스템은 정교해질 뿐 성장하지 않는다.

§ 12 — Halting & Recovery

중단과 회수

중단은 실패가 아니라 위임 계약의 회수 트리거가 작동한 것.

12.1정량적 회수 트리거

회수 조건이 정량화되지 않으면 계약이 실행되지 않는다. 이 프로젝트의 회수 트리거는 다음이다.

트리거임계치단계
같은 테스트 반복 실패2회즉시 중단
수정 루프 반복2회 초과즉시 중단
변경 파일 수10 / 15 / 초과경고 / 재승인 / 중단
의미 있는 diff 크기500 / 800 / 초과경고 / 재승인 / 중단
영향이 새 서비스로 확장1개라도즉시 중단
요구사항과 구현 사이 충돌즉시중단
보안·권한 영역 진입즉시강제 층 차단
테스트 삭제·약화 시도즉시강제 층 차단
확신도 임계치 하락< 0.5재승인

12.2단계적 회수

모든 회수가 즉각적이지 않다. 세 단계로 유연성 유지.

  • 경고 단계. 임계치의 절반. 로그만 남기고 진행.
  • 재승인 단계. 임계치 도달. 사람에게 진행 여부 확인 요청.
  • 중단 단계. 임계치 초과. 즉시 중단하고 인계 패킷 출력.

12.3인계 패킷

중단 시 에이전트가 코드를 더 만들지 않는다. 대신 다음을 출력한다.

  • 현재 상태. 어디까지 진행됐고 지금 무엇이 걸려 있는지.
  • 실패 원인 후보. 왜 이 지점에서 막혔는지의 가설.
  • 시도한 것. 어떤 접근을 해봤고 각각 왜 실패했는지.
  • 새로 발견한 범위. 처음 예상과 다르게 커진 부분.
  • 사람이 결정할 선택지. 이 지점에서 가능한 여러 방향과 각각의 트레이드오프.
  • 계약의 어떤 부분이 회수됐는지. 어떤 트리거가 작동했는지 명시.
중단이 없는 자동화

몇 사이클 동안 중단이 한 번도 관찰되지 않으면 시스템이 완벽한 게 아니라 회수 조건이 너무 느슨한 것이다. 실제 개발에는 애매한 상황이 반드시 있고, 그때 중단이 트리거되어야 정상이다.

§ 13 — Principle vs Implementation

원칙과 구현의 분리

이 명세서가 남기는 것은 도구 매뉴얼이 아니라 판단의 지도.

13.1이 명세서에서 도구 이름이 최소인 이유

이 명세서는 특정 도구 이름을 최소로 유지한다. Claude Code, GitHub Actions, MCP 같은 이름이 등장하지만, 이 도구들이 명세서의 정의는 아니다. 이것들은 현 시점의 구현일 뿐이다.

원칙은 "무엇을 왜 그렇게 하는가"이다. 구현은 "그것을 어떤 도구로 어떻게 하는가"이다. 이 둘을 문서 안에서 섞으면 도구가 바뀔 때 원칙도 흔들린다.

13.2원칙과 구현의 예시 분리

원칙 (Policy)

위험 명령은 실행 전에 결정적으로 차단한다.

이 원칙은 도구가 바뀌어도 유지된다.

구현 (Implementation)

현재: Claude Code PreToolUse hook + .claude/settings.json

대안: shell wrapper CLI · container seccomp · CI permission scope

13.4이 명세서의 지향

이 명세서가 지향하는 것은 매뉴얼이 아니라 판단의 지도다. 새 도구가 등장하거나 프로젝트 조건이 바뀌었을 때, 이 지도가 방향을 가리킨다. 도구 자체의 성능이나 유행이 아니라 이 명세서의 원칙에 비추어 판단한다.

도구는 시대에 따라 바뀌지만, 위임 계약 위에서 협업하고 관찰과 개정으로 학습한다는 결정은 그대로 유지된다.
