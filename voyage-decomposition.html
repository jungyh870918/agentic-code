Decomposition Specification

기계가 거르는 두꺼운 층, 사람이 판정하는 얇은 층

이 문서는 SPEC 01에서 확립한 에이전틱 오케스트레이션 철학을 실재하는 프로젝트 Voyage에 정착시키기 위한 분해 명세다. 기능 단위가 아니라 시스템 정착 단위로 프로젝트를 해체하고, 각 조각을 자동화 스펙트럼 위에 배치한다. 핵심 발견은 — Voyage의 기계 레이어는 이미 스크립트로 존재하며, 정착 작업의 무게중심은 코드 작성이 아니라 검증 게이트와 라우팅 규칙을 얹는 데 있다는 것이다.

§ 00 — Scope

범위 — 분해란 무엇인가

SPEC 01이 추상 거버넌스 설계라면, 이 문서는 그 설계를 실재 프로젝트에 적용한 분해다.

00.1왜 분해가 먼저인가

Voyage는 기능이 거의 완성된 회화 암기 앱이다. 이를 오케스트레이션 시스템에 정착시키려면, 먼저 프로젝트를 시스템이 다룰 수 있는 조각으로 해체해야 한다. 중요한 것은 분해의 기준이 "기능"(기획·디자인·코딩·배포·콘텐츠)이 아니라는 점이다. 같은 기능 안에도 자동화 가능한 부분과 사람이 반드시 쥐어야 할 부분이 섞여 있기 때문이다.

그래서 분해의 단위는 정착 단위다 — "이 작업을 시스템의 어느 레이어가, 어떤 게이트를 거쳐 처리하는가"가 같은 것끼리 묶는다. 이 문서는 11개의 실무 자료를 관통해 도출한 5조각 분해를 확정하고, 그 위에서 정착 순서를 정한다.

Core Finding

Voyage의 기계 레이어는 이미 스크립트로 존재한다. 정착이란 새 코드를 짜는 일이 아니라, 기존 블록 위에 검증 게이트와 라우팅 규칙을 얹는 일이다.

00.2증명 포인트의 계승

SPEC 01의 증명 포인트는 "프로세스 추적 가능성"이었다. Voyage에서 이것은 더 구체적인 형태를 띤다 — 모든 레슨과 그 파생 데이터가 단일 소스(batches/*.json)에서 결정론적으로 유도되고, 그 유도 과정이 검증 게이트로 보증되는 것. 진실의 원천이 사람의 머릿속이나 파일 주석이 아니라, 검증 가능한 데이터에 있어야 한다.

§ 01 — Two Blades

분해의 두 칼날

프로젝트를 가르는 두 기준 — 어디에 게이트를 두는가, 누가 판정하는가.

01.1첫째 칼날 — 가역성 × effect 종류

SPEC 01에서 가져온 원칙이다. "잘못되면 되돌리는 데 얼마 드는가"가 게이트를 정한다. 단, 외부 검토를 거치며 가역성만으로는 부족하다는 것이 확인됐다 — 기술적 롤백 가능성과 실제 피해의 가역성은 다르다. 코드는 revert되지만, 발송된 이메일·노출된 시크릿·사용자가 외운 문장은 되돌릴 수 없다. 그래서 가역성은 effect 종류(pure / idempotent / compensatable / cost-incurring / credential-bearing / non-compensatable)의 한 변수로 다룬다.

01.2둘째 칼날 — 결정론적 검증 가능성

두 외부 리뷰어(ChatGPT·Gemini)가 독립적으로 합의한 핵심 분기다. "결과물을 기계가 검증할 수 있는가"가 자동화의 경계선이다. 개발 도메인은 컴파일러·린터·테스트라는 기계적 판독관이 1차 실수를 걸러준다. 그 판독관이 있는 작업은 자동화에 가깝고, 없는 작업(가치 판단·실기 동작)은 사람에 가깝다.

이 두 칼날로 Voyage를 가르면, 작업들이 자동화 스펙트럼 위에 자연스럽게 흩어진다. 그 결과가 다음 섹션의 5조각이다.

두 칼날은 직교한다. "자유 가역이지만 검증 불가"(예: 플레이어 음원 동작)와 "준 비가역이지만 검증 가능"(예: migrate)이 모두 존재한다. 그래서 단일 축이 아니라 다축 분류가 필요하다 — §03 참조.
§ 02 — Five Pieces

다섯 조각 (A–E)

Voyage를 정착 단위로 해체한 결과. 각 조각은 자동화 가능성이 극과 극으로 다르다.

02.1조각 A — 정합성 검증 기계 · 자동

결정론적으로 검증 가능하고 부작용이 0인 작업. 스키마 검증(dialogue 20턴, expr 4 / pron 3 / react 4), 영역 간 중복 검사, dialogue 포함 검사, 안전성 블랙리스트, 이미지 계약(이름·동기화) 검증, 파생 데이터 정합성. Voyage의 voyage_content_orchestration.md에 이미 "코드로 강제, LLM 신뢰 금지"로 명시된 검증 함수들이 여기 속한다. 이 조각은 시스템의 척추이자 자동화 1순위다 — 모든 다른 조각이 마지막에 이 게이트를 통과해야 안전하게 배포된다.

02.2조각 B — LLM 생성·평가 실행 + 판단

LLM이 판정하되 사람이 결정하는 영역. 3-LLM 병렬 생성·교차 평가·합성, 루브릭 채점, 난이도 정규화, 정제. 핵심은 생성자≠검증자 — 생성한 모델이 자기 결과를 채점하지 못하게 강제한다. 단, 이 조각은 근거를 쌓는 단계지 결정 단계가 아니다. 점수와 정제안을 만들어 사람 앞에 내려놓는 것까지가 에이전트의 몫이다. 채점 시스템의 삼중 구조(순수 LLM 판단 + 사람이 심은 결정론적 닻 + 절충 규칙)가 이 조각의 정교한 사례다 — §05.3.

02.3조각 C — 가치 판정 사람 전용 · 기계 금지

점수로 환원 불가능한 가치 판단. "이 문장을 들으면 장면이 그려지는가"(텍스트), "이 삽화가 이 대화 상황·화자 성별에 맞는가"(이미지), "이 대화가 20대 톤인가 30대 톤인가"(화자). 루브릭 88점이어도 장면이 안 보일 수 있다. 이 조각은 시스템화의 대상이 아니라, 시스템이 침범하지 못하게 보호해야 할 사람의 자리다. 여기서 "1초 게이트"가 의식(ritual)으로 전락하는 위험이 가장 크다.

02.4조각 D — 비용·비가역 게이트 effect가 게이트 요구

검증 가능성과 무관하게 effect 자체가 게이트를 요구하는 작업. ElevenLabs TTS 캐시 미스(비용), 이미 출시된 레슨 변경(사용자가 외운 것 — 준 비가역), migrate(DB), 앱 빌드(준 비가역). 이 조각의 핵심 함정은 겉보기 가역성과 실제 effect의 괴리다 — 예: age_group 필드 하나를 바꾸면 화자가 바뀌어 대량 캐시 미스가 발동한다(§05.2).

02.5조각 E — 런타임 검증 실기 필수 · 자동화 제외

오직 실기에서 돌려봐야만 아는 비결정 영역. 플레이어 오디오 동작, iOS WebView 제약(volume 무시, safe-area), 환경별 차이, <audio loop> Range 충돌. 컴파일·린트·CI로 안 잡히고, LLM이 코드를 읽어도 "작동함"을 확인 못 한다. 시뮬레이터조차 마이크·오디오·safe-area를 못 잡는다. 이 조각은 자동화에서 영구 제외하고 Local Loop(사람+로컬 터미널)에 남긴다.

§ 03 — Four Axes

네 개의 직교 축

5조각은 작업의 성격이고, 그 성격은 네 개의 독립된 축으로 측정된다.

11개 자료를 관통하며, 조각을 가르는 축이 하나가 아니라 넷임이 드러났다. 이 네 축은 직교한다 — 한 작업이 각 축에서 독립적으로 평가된다. 그리고 조각 A는 네 축 모두의 안전한 끝에, 조각 E는 모두의 위험한 끝에 위치한다는 것이 분해의 핵심 정합성이다.

축안전한 끝위험한 끝측정하는 것
1. 검증 가능성기계 검증 (A)실기·가치 (C·E)기계가 결과를 거를 수 있는가
2. 가역성자유 가역 (A)준 비가역 (D·E)되돌리는 실제 비용
3. 시크릿 노출무시크릿 (A)데이터·비용 키 (B·D)건드리는 자격증명 등급
4. 배포 채널git push (가역)스토어 (준 비가역)외부 게이트 종속성

03.1시크릿 축 — VITE_ 접두사가 경계선

Voyage에서 신뢰 경계는 추상이 아니라 물리적 경계로 구현돼 있다. VITE_ 접두사가 붙은 환경변수만 클라이언트 번들에 노출된다 — 즉 접두사가 공개/비공개의 경계선이다. OPENAI_API_KEY·ELEVENLABS_API_KEY·R2_SECRET·DATABASE_URL 같은 7종의 시크릿은 서버에서만 읽힌다. 외부 검토의 처방대로 — 이 시크릿들은 LLM 컨텍스트에 직접 들어가면 안 되고, 격리된 실행기(tool proxy)가 사용해야 한다. 조각 A가 시크릿을 전혀 안 건드린다는 점이 자동화 1순위의 또 다른 근거다.

03.2배포 채널 축 — push와 스토어의 분리

Voyage의 아키텍처는 영리하게도 "비싼 것"과 "싼 것"을 이미 분리해놨다. 콘텐츠·음원·정적 오디오·백엔드는 git push만으로 Railway가 빌드·반영한다(가역, 앱 빌드 불필요). 진짜 준 비가역(앱 스토어 빌드·심사·계정 승인)은 프론트 코드 변경 때만 발동한다. 콘텐츠 파이프라인 전체가 git push 이하에 머물러, 스토어 게이트를 안 건드리고 무한 반복 가능하다. 이것이 콘텐츠 축을 자동화 1순위로 두는 결정적 근거다.

Convergence

조각 A는 네 축 모두의 안전한 끝에 있다 — 기계검증 · 자유가역 · 무시크릿 · push 이전. 자동화 1순위가 네 번 독립적으로 확인된다.

§ 04 — Layer Mapping

4레이어 매핑과 헤더 권한

5조각을 SPEC 01의 4레이어에 얹고, 미결이었던 헤더 권한을 확정한다.

04.1헤더가 짤 코드는 거의 없다

SPEC 01에서 헤더는 "직접 생산하지 않는 지휘자"였다. Voyage에서 이것이 극적으로 확인된다 — 변환·빌드·배포 스크립트(batches_to_content.py, migrate_content.py, generate_all.py, npm run build, cap sync)가 이미 전부 존재한다. 헤더의 일은 새 코드를 짜는 게 아니라, 이 기존 블록들을 가역성·비용 조건에 따라 언제 어떤 순서로, 어떤 게이트를 통과시켜 트리거하는가의 라우팅이다.

04.2미결 확정 — 헤더는 중앙 Orchestration이다

SPEC 01의 단 하나 남은 미결 사항은 헤더가 중앙 지휘자(orchestration)냐 첫 트리거만 당기는 자(choreography)냐였다. 외부 리뷰어 둘이 이 지점에서 갈렸다. Voyage가 답을 확정한다 — 중앙 orchestration.

  • 순차 의존: 모든 축의 스크립트가 순서 의존이다. batches → content → migrate, png → 800.webp → blur. 누군가 순서를 쥐어야 한다.
  • 수작업이 이미 순차 지휘: 현재 사람이 STAGE 1 돌리고, 결과 보고 STAGE 2 돌리고, 합성한다. 자율 반응이 아니다.
  • 관통 작업: age_group 변경 한 번이 조각 A→C→D→A를 순서대로 관통한다(§05.2). 중앙에서 순서를 쥐지 않으면 비용 게이트를 건너뛴다.
  • 짝 제약: 서로 다른 가역성 등급의 작업이 동시 발화돼야 한다(§05.4). 자율 반응으론 빠른 쪽이 먼저 나가 공백이 생긴다.
Resolution

헤더의 진짜 일은 "이 작업이 어느 조각인가"가 아니라 "이 작업이 어느 조각들을 어떤 순서로, 어떤 짝과 함께 통과해야 하나"의 라우팅이다.

§ 05 — Consistency Graph

정합성 그래프와 짝 제약

레슨 하나의 변경은 단일 작업이 아니라, 파생 데이터 전체의 원자적 갱신이다.

05.1레슨 변경 = 정합성 그래프 갱신

레슨 객체 하나에서 timeline.json(음원)·quality_scores.json(채점)·lesson_intros.json(인트로+블러)이 파생되고, 채점 메타(references·critical_keywords)가 별도 주입된다. 그래서 "레슨 변경"은 단일 작업이 아니라 정합성 그래프 전체의 갱신이다. 레슨을 바꿨는데 timeline은 갱신되고 quality_score는 옛 점수가 남으면, 시스템이 일관성 깨진 중간 상태에 빠진다.

05.2관통 경로 — age_group의 위험

분해에서 가장 조심할 사례. age_group은 batches JSON의 필드 하나라 겉보기엔 자유 가역이다. 그러나 이를 바꾸면 화자(voice)가 바뀌어 그 레슨의 모든 영어 문장이 캐시 미스 — 즉 비용(조각 D)이 발동한다. 에이전트가 "필드 수정이니 자유 가역"이라 순진하게 판정하면 조용히 비용을 터뜨린다. 그래서 이 작업은 단일 조각이 아니라 4스텝으로 분해된다.

# age_group 변경 한 번이 관통하는 경로
조각 A  카테고리 폴백 기계 제안
  → 조각 C  톤·삽화 일치 사람 확인
    → 조각 D  blast_radius·비용 예측 게이트
      → 조각 A  실행: migrate + generate_all

외부 리뷰의 게이트 함수 f(effect_type, blast_radius, cost…)가 여기서 구체화된다. 텍스트 한 줄 수정은 문장 1개만 캐시 미스(작은 blast), age_group 변경은 레슨 전체(큰 blast). 시스템은 변경 전에 blast_radius를 계산해 게이트를 띄워야 한다.

05.3조각 B의 삼중 구조 — 채점 시스템의 교훈

채점 시스템은 "LLM 단독 판단은 게이트가 될 수 없다"를 독립적으로 증명한 사례다. 임베딩 cos만으로는 "세련되게 바꾼 정답"과 "구조만 같은 오답"을 못 가른다(둘 다 cos 0.6~0.75에 섞임). 해결은 사람이 심은 결정론적 닻이었다.

  • references(패러프레이즈): max-cos로 "세련된 정답"을 위로 구제 — 관대함.
  • critical_keywords(핵심어): 누락 시 cap으로 "구조만 같은 오답"을 차단 — 변별력.
  • paraphrase_matched 예외: 둘을 절충 — 정답이 cap에 억울하게 안 걸리게.

이 삼중 구조(흔들리는 LLM 판단 + 결정론적 닻 + 절충 규칙)가 조각 B의 본질이다. 단, 닻을 만드는 메타데이터 자체를 LLM이 생성하므로 — 메타데이터 생성은 B, 그 검증의 경계 사례는 C(사람)로 올라간다. 부정확한 references는 오답을 정답으로, 부정확한 keywords는 정답을 오답으로 만들기 때문이다.

05.4짝 제약 — 가역성 경계를 가로지르는 원자성

실무에서 가장 자주 무는 함정. 서로 다른 배포 채널에 걸친 작업이 동시에 발화돼야 하는 경우다.

짝빠른 쪽느린 쪽먼저 하면
intro_kr 제거 ↔ 미리보기 모달음원 (git push)모달 (앱 빌드)안내 공백
썸네일 fade-injsxcss (짝)썸네일 안 뜸

서로 다른 채널(Railway 즉시 vs 스토어 며칠)은 원자적으로 묶을 수 없다. 그래서 헤더는 짝을 인식하고 느린 쪽(앱 빌드) 시점에 빠른 쪽을 묶어 동시 발화해야 한다. 이것이 중앙 orchestration이 필요한 가장 실전적인 이유다.

§ 06 — Local Loop

Local Loop · Global SSoT

"만들 때는 자유롭게, 합칠 때는 무자비하게" — git push가 경계선이다.

외부 리뷰 둘이 합의한 결합 구조다. Voyage의 두 접근([A] 자율 시스템, [B] 사람 허브)은 경쟁이 아니라 push 시점을 경계로 한 샌드위치다. 인프라가 이를 그대로 뒷받침한다 — 로컬은 프론트(5173)·백엔드(8000) 별도 프로세스에 .env 파일, 배포는 Railway 한 덩어리에 대시보드 env 주입.

이 구조가 첫 질문 — "Kun의 셋업에 쓸 정보가 있나"의 최종 답이기도 하다. Kun식 로컬 터미널 환경(worktree·음성입력·실기 탐색)은 Voyage 시스템의 로컬 입력단으로 들어간다. 대체하거나 충돌하는 게 아니라, Local Loop를 담당하는 조종석이다. 특히 조각 E(플레이어 런타임)처럼 실기 탐색이 필요한 영역에서 Kun식 접근이 빛난다.

§ 07 — Settlement Order

정착 순서 — Phase 0부터

분해가 닫혔으니, 이제 어떤 순서로 시스템에 앉히는가. 가역성 순으로 정착한다.

외부 리뷰가 공통으로 경고했다 — "거버넌스 선언이 런타임 보장을 앞서가면 안 된다." 그래서 Temporal 같은 무거운 백본을 먼저 깔지 않는다. 측정과 검증 게이트부터, 작게 시작한다.

PHASE 0정합성 검증 게이트조각 A · 무시크릿 · 자유가역

자동화가 아니라 검문소 세우기. 기존 124레슨을 건드리지 않고 지금 당장 가능하다. 네 축 모두의 안전한 끝이라 위험이 가장 낮다.

  • 의사코드 검증 함수 3개를 강제 코드로: validate_schema · check_no_duplicates · check_all_in_dialogue
  • check_all_in_dialogue의 정규화 규칙 확정(축약·구두점·대소문자)
  • 파생 데이터 정합성 검증(해시 세대 비교) 추가
  • 안전성 floor(욕설·모욕 블랙리스트)를 LLM 이전 정적 필터로
  • 이미지 계약 검증(이름·png+webp+blur 동기화) · 오디오 경로 floor
PHASE 1측정 + LLM 평가조각 B(평가)

기존 레슨에 대해 돌려도 안전(점수만 매기지 콘텐츠 불변). 외부 리뷰가 강조한 측정 기반을 먼저 쌓는다.

  • 생성자≠검증자를 코드로 강제한 루브릭 채점 파이프라인
  • 경계선(68~72, 88~92)만 교차검증 — 기존 규칙 그대로
  • 측정: 채점 흔들림 · 비용 · latency · 사람 수정량 · 재채점률
  • 중복 실행 방지: GitHub Actions concurrency group(Phase 1엔 충분)
PHASE 2생성·정제 오케스트레이션조각 B(생성) + D

수작업 3-stage(생성→평가→합성)를 중앙 헤더가 순차 트리거. 오버나이트 배치(gnhf 패턴)로 124레슨 대량 처리, 아침에 사람은 장면 게이트만.

  • refine_stage 상태 추적 추가(0=raw … 4=검수완료) — 비멱등·중복 정제 방지
  • scene_verified 사람 게이트 명시(조각 C — 1초 거부)
  • 비용 게이트: age_group·텍스트 변경 시 blast_radius 사전 계산
  • 두 파이프라인(콘텐츠·음원)이 동시에 돌기 시작하면 → 별도 상태 레이어(Postgres task table) 도입 검토
보호자동화하지 않는 것조각 C · E

이 둘은 시스템화 대상이 아니라 보호 설계다 — 자리를 비워두거나 게이트를 세워둔다.

  • 조각 C(장면·삽화·톤 판정): 사람 자리로 비워둠. 점수 1초 승인으로 대체 금지.
  • 조각 E(플레이어 런타임): Local Loop에 남김. 실기 검증은 사람이 디바이스로.
  • 메타데이터 경계 사례(references/keywords): 생성은 B, 검증은 C로 에스컬레이션.
  • 준 비가역(앱 빌드·출시 레슨 변경): 사람 게이트 + 짝 묶음 발화.
